# Repo boundaries: capture-tool and ZED appliance extraction

## Scope

The repo-boundaries thread of the polyrepo initiative ([index](polyrepo.md)): extract the phone-side capture tool and the ZED box appliance into a **single** standalone repo — `placeframe-capture-tool`, one repo rather than a phone/box pair: the AOA tether couples the phone app to the box stack, and same-repo consumption keeps `PlaceframeZedCaptureClient`'s only in-repo consumer co-located — define the cross-repo contracts, and hold the fresh-clone-autonomy invariant. Siblings: [prepo, the polyrepo workbench](polyrepo-workbench.md) and [publishing](package-publishing-redesign.md).

## Problem

The capture tier becomes one standalone repo. Cross-repo consumption is registry consumption — which makes the publishing thread load-bearing rather than cosmetic: a broken publish no longer costs external visibility, it blocks the other repos' development loops. The extraction is the event that converts sibling consumption from intra-repo `file:` refs to registry pins. Local iteration across repos rides those same registry pins plus prepo's `sync` provisioning; the git-filter dependency overlay once planned as the local-iteration mechanism was deleted from prepo before this thread began (undercooked, undesirable complexity — operator ruling 2026-09-20), so no overlay exists to exercise.

## Design

### Extraction

| New repo | Takes | Publishes |
|---|---|---|
| `placeframe-capture-tool` | `apps/CaptureTool/`, the `capture-tool-v*` tag prefix, `unity-build.json`, the AOA Java/OkHttp client + handler, the log relays, the `install --project CaptureTool` flow, `docker/zed-capture/`, `docker/aoa-bridge/`, `docker/aoa-gateway/`, box `loki`/`alloy` configs, `compose.rig.yml`, the zed targets of `compose.zed.bake.yml`, `placeframe-zed.service`, `wait_for_zed_camera.py`, `install-zed` (`scripts/src/scripts/install_zed/`), zed-capture-client generation (via openapi-client-codegen's shared orchestrator verb) | APKs, `PlaceframeZedCaptureClient` (nuget + npm), box images (`ghcr.io/outernet-foundation/placeframe-capture-tool/*`) |

placeframe keeps the server stack, the UPM SDK (`Core`, `ARFoundation`, `MagicLeap`, `Auth`, `Logging`), api-client generation, and MapRegistrationTool as an in-repo consumer — the `file:` consumption path stays exercised where it remains intra-repo. The top-level `zed/` tree is dead (its `src/` contains only `__pycache__`): delete it, do not move it.

### Client generation in the capture repo

The capture repo consumes openapi-client-codegen for zed-capture-client generation and publishing; placeframe's `generate-clients` drops the zed project entry at cutover. The orchestration itself (spec dump → downgrade → committed-spec skip → generate) moves **into openapi-client-codegen** as a shared verb — neither repo keeps a local copy (see the duplication audit).

### Contracts

Four contracts cross boundaries. With phone and box in one repo, two cross repo boundaries and two cross field-deploy boundaries. **Compat policy (operator ruling 2026-09-21): paired versions** — a change to any shared surface (the zed-capture API, the AOA transport, log-drain semantics) ships phone and box together as a matched pair; mismatched pairs are unsupported, not engineered against, and there is no additive-only CI gate. Phone-only changes — the common case — never require a box update. The committed `openapi.json` remains the record of what a matched pair speaks. One authoritative home per contract, referenced — never duplicated — by the relevant agent docs:

1. **Capture tar** (`rig*/frames.csv` + stereo JPEGs + factory calibration) — box → placeframe reconstructor. **Cross-repo.** Home: the wire types in `placeframe-core` (PyPI).
2. **zed-capture REST API** — box → phone. The committed `openapi.json` is the machine-checkable artifact and the compat gate; the phone pins a `zedcaptureclient` version. **Intra-repo, field-deploy boundary.** Home: the capture repo (spec + generated client).
3. **AOA transport** (h2c prior-knowledge over the accessory FD, bridge forwarding to `127.0.0.1:9000`) — phone ↔ box. **Intra-repo, field-deploy boundary.** Home: the capture repo (bridge + phone handler are the reference).
4. **Log drain** (box-clock semantics, restamp at the push boundary) — box → phone → backend. Box→phone is intra-repo; the backend ingestion edge is **cross-repo**. Home: split — box-clock/restamp semantics in the capture repo, the ingestion edge in placeframe.

### Public accessibility

The capture repo is a public end-to-end artifact: its README documents the hardware to buy (ZED X with global shutter, ZED Box, power bank, Android phone) and the install-and-scan steps for anyone holding those components. Everything the flow needs is therefore publicly consumable — the APK from GitHub Releases, the UPM/nuget/npm packages (already publishing publicly), the PyPI deps, and the box images as public GHCR packages in the repo's namespace (the standing practice: the same image set already publishes publicly under `placeframe/*`). The Stereolabs-derived `zed-capture` image is part of that public set today; deriving custom images from `stereolabs/zed` is the vendor-documented use of it (their own Docker guides build FROM it; their Dockerfile repo is MIT), with the SDK EULA binding each runner of the image, as it already does.

### Fresh-clone autonomy (hard requirement)

Every repo, cloned alone, with the standard toolchain: builds green, `git status` clean, prepo unknown to the cloner. Nothing prepo-related is committed anywhere — with the overlay deleted, prepo never writes manifests and leaves no per-clone state (no filters, attributes, or hooks) for `git clone` to transfer. CI is the no-prepo user — it is a fresh lone clone by construction. The structural backstop remains: a `file:` ref or out-of-repo path source that somehow reached a commit cannot resolve in a fresh clone, so CI fails loudly.

## Discarded alternatives

- **Two repos (phone app + box stack)**: the AOA tether couples the phone app to the box stack, and a split puts `PlaceframeZedCaptureClient`'s only in-repo consumer across a registry boundary — a published package with exactly one consumer that lives in the same repo. One repo (operator ruling; the index carried it before this doc caught up).
- **Vendoring `common`/`core` into the capture repo**: duplicates the capture-tar wire-contract types (`CaptureSessionManifest` and friends); drift there is a broken inter-repo contract, not a compile error.
