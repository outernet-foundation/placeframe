# prepo: the polyrepo workbench

## Scope

The prepo thread of the polyrepo initiative ([index](polyrepo.md)): expand pgit into **prepo** (final name, decided) — from git porcelain to the polyrepo workbench, in two halves:

1. **Workspace transparency** — the VSCode multi-root pane always shows every repo and worktree in the workspace folder, correctly named and grouped, with zero operator action.
2. **Local dependency overlay** — swap any registry dependency for a local, live-editable sibling checkout, per developer, without git noise at rest and without breaking fresh-clone autonomy. **Deleted after landing** (operator ruling 2026-09-20: undercooked, its complexity undesirable at this time) — see item 20; registry pins are the standing consumption story.

The existing six verbs survive; `new`/`drop` are re-scoped (below). Siblings: [publishing](package-publishing-redesign.md) and [repo boundaries](repo-extraction.md).

## Problem

Local iteration:

1. A developer iterating across repos must be able to swap any registry dependency for a local, live-editable sibling checkout — per developer, without git noise at rest, and without breaking the guarantee that **any single repo clones, builds, and stays `git status`-clean with no knowledge of prepo**.

Workspace pane:

2. The pane reflects workspace reality **without operator action**: every repo under the workspace root and every worktree appears, disappears, and renames itself as topology changes — regardless of which actor changed it (pgit, raw git, an agent, another machine through the bind mount).
3. Folder titles are disambiguated **everywhere** VSCode shows them — a worktree is always titled `<repo>: <branch>`, never a bare branch name that loses its repo context outside the Explorer pane.
4. Nothing member-shaped is committed: the workspace template carries only VSCode payload (settings, extensions, launch config); the generated workspace file is machine-local.

## Ground truth

### Ecosystem override capabilities

How each ecosystem supports "registry by default, local path for the packages under iteration" — per official docs and tracker threads:

- **uv**: `[tool.uv.sources]` is the only source-override mechanism and it must live in `pyproject.toml` — not `uv.toml`, not env vars, not CLI flags; the maintainers have declined otherwise on lockfile-coherence grounds ("sources outside the pyproject would invalidate the lockfile"; astral-sh/uv #6772, #11632, #12013, #15895). The lock records path sources while they are active.
- **uv sync/uv run validate installation provenance, not just name+version** (verified 2026-09-19 on uv 0.11.14, scratch two-repo repro): an editable install shadowing a declared, locked dependency is evicted and reinstalled from the lock by the next `uv run` — and by `uv sync --inexact`, which suppresses only extraneous-package removal, not source revalidation. Consequence: a venv-level overlay cannot survive the everyday commands, and conversely, restoring the locked manifests self-heals the venv on the next run with no install command.
- **Cargo**: `[patch]` may live in `.cargo/config.toml`, which cargo discovers by walking up parent directories; the Cargo Book states config-file patching is "generally only appropriate when the patch section is automatically generated by an external build tool," and relative paths resolve from the config file. An overlay above all checkouts is therefore first-class.
- **Go**: `go.work` is per-developer, discovered by walking up, and the workspace design proposal both says not to commit it and anticipates that "the creation of the file can be automated by an external tool that scans for all the go.mod files recursively." CI runs with `GOWORK=off`.
- **Unity/UPM**: no per-user or local override layer exists (Unity staff confirmation on the 2021 `manifest.local.json` request: "There's nothing in place to allow what you want to do here"). The one structural override: a package embedded under the project's `Packages/` directory shadows the same-name registry entry. Separately, `file:` and git dependencies are treated by the SAT solver as overriding any version constraint, and `file:` paths may traverse outside the project.

(npm dist-tag behavior — floating pointers, no Unity resolver concept — is recorded in the publishing doc, where it is load-bearing for the dev-channel interface.)

### Git filter mechanics (verified 2026-09-19, git 2.43.0, scratch repo)

- **The hide works**: with a clean filter registered (local config `filter.<name>.clean` + `.git/info/attributes`) and the index stat refreshed, a worktree whose manifest carries `file:` refs reports `working tree clean` with an empty diff. Git's records hold registry-shaped content; the worktree holds linked content.
- **The dirty check short-circuits on raw size before consulting the filter**: rewriting the worktree without refreshing the index shows `modified` with an empty diff (the classic LFS symptom). After applying a link — and after uv/Unity rewrite the lock files — a no-op `git add` of the two files must refresh the stat cache.
- **smudge re-derives the link across checkouts**: branch switches re-materialize the manifest through the filter; the worktree stays linked against each branch's committed content. Nothing collides with the link, because git does not consider the linked file dirty.
- **clean runs on effectively every status/diff/add touching the file** (status did not persist its stat refresh across back-to-back invocations). Filter stderr does reach the terminal, so a "you are linked" message would print on every invocation, including shell-prompt and IDE background traffic — filters are unusable as a messaging channel, and a broken `required` filter fails status, not only writes (accepted under strict mode).
- **A stateless clean filter breaks when HEAD moves** (verified with a hardcoded-pin toy filter): the inverse must be derived from HEAD (`cat-file`). Calling git from inside a filter is documented-deadlock territory — gate #1 for the battery, with prepo-maintained shadow snapshots of expected-clean content as the fallback.
- **git aliases cannot shadow builtins** (`alias.status` silently ignored) and there are no hooks on read-only commands: no git-config-side way to decorate `git status`. Messaging lives in mutation hooks and the shell prompt.

### Filter gate battery results (verified 2026-09-19, git 2.43.0, scratch repos)

All three gates **pass**; the filter design stands with the shadow-snapshot fallback retired:

- **`cat-file`-from-inside-clean does not deadlock.** A clean that shells `git cat-file blob HEAD:<path>` (path via the filter command's `%f` placeholder) ran through `status`, `diff`, `add`, `commit`, branch switches, merge (incl. conflicts), and stash under a 10 s timeout guard — nothing hung.
- **Merge/stash round-trips stay in the linked domain.** Stash push stores the cleaned registry+residue and restores the linked worktree; pop reapplies residue onto it; dirt after pop is residue only. Conflict markers materialize in the *linked* domain (context linked, both sides' residue present) — resolution happens where the developer lives, `git add` cleans to registry + resolved residue. A resolved-and-committed manifest records exactly registry + residue, status clean.
- **Worktrees pick the overlay up for free; clones are born clean.** `git worktree add` shares the local config (filter found) and `git rev-parse --git-path info/attributes` in the worktree resolves to the shared common attributes file — the fresh worktree materializes linked. A fresh clone carries neither config nor attributes, and because git's records are registry-shaped it checks out registry content with a clean status — fresh-clone autonomy holds by construction, not just by fallback.

Implementation caveats the battery surfaced (binding on item 11):

- `git checkout -- <path>` on an *existing* file can skip the smudge (stat-cache short-circuit); re-materialization must go through rm+checkout or rely on the prescribed no-op-`git add` stat refresh.
- A residue-blind clean silently drops authored changes at `add` — the real clean must derive the link-hunk inverse from HEAD and merge residue through, never replace wholesale.
- `cat-file` fails on paths absent from HEAD (new filtered files, unborn HEAD on a first add): clean must pass worktree content through untouched when HEAD lacks the path, else `required = true` bricks the first commit of a new manifest.

### VSCode workspace mechanics (documented platform behavior; verified during the original workspace redesign)

- Multi-root `folders` is a literal array — no globs, no includes, no auto-discovery; a folder gets first-class treatment (Explorer root, own SCM provider, own analysis scope) only by being listed. `git.autoRepositoryDetection` populates only the Source Control view. (Design source: [pulsar `design/workspace-redesign.md` §5.4–5.5](../../pulsar/design/workspace-redesign.md).)
- Folder entries accept a `name` field, and that name is what the workbench propagates wherever it titles the folder: Explorer root label, quick-open folder picker, search-scope labels. It is the one lever for "disambiguation everywhere."
- `vscode.workspace.updateWorkspaceFolders()` adds/removes roots at runtime, live, with no reload — and is **not persisted** to the workspace file; the file is only re-read on window open.
- A workspace file changed on disk mid-session prompts "workspace file changed — reload?" — at-rest writes by the extension occasionally trigger it; the resulting reload is a no-op when the runtime delta already applied. Accepted cost.

### Observed defects (2026-09-19)

- The committed `main.code-workspace` in the code-workspace repo sat mid-rebase with unresolved conflict markers: machine output under version control, regenerated per-machine against per-machine topology, colliding textually. VSCode could not parse the pane definition at all.
- Its conflicted content still listed worktrees deleted earlier: topology mutations outside `pgit new`/`drop` (raw git, the other bind-mount view) never regenerate the file — regeneration fired only as a `new`/`drop` side-effect.
- The template's pinned list had drifted in both directions: five workspace repos unpinned, one pinned repo absent from disk; the repo's history was a stream of "Pin X in workspace template" chores.

## Design

### Placement and scope

pgit expands into prepo (final name) from git porcelain to polyrepo workbench. The existing six verbs survive — `status`, `new`, `drop`, `fetch`, `pull`, `push` — with one amendment: `new`/`drop` shed workspace regeneration (below). The overlay cohort (`link`/`unlink`, later joined by `bump`/`doctor`/`detach`) is gone — item 20; the surviving additions are `regenerate-workspace` and `sync` (dependency provisioning — parallel `uv sync` per Python checkout root, serial Unity batch no-op refresh per Unity project). The scope wall moves from "language-agnostic, no environment provisioning" to **language-aware, build-agnostic**: prepo reads and writes package-manager manifests; it never runs builds, installs, or editors (`uv sync`, `npm install`, Unity remain the caller's commands). This keeps the tool testable with scratch repos and keeps build semantics inside each ecosystem's own tooling. prepo does not assume pgit's branch==worktree model — that convention serves agentic concurrency and remains an opt-in tier; checkouts are a first-class, dynamic set (root checkout, any worktrees, independent clones under the workspace), and link intent applies to all of them, reconciled per checkout.

### Workspace transparency

#### Template = VSCode payload only

The template keeps its path and filename (it is the workspace-root marker for discovery) and loses everything member-related — no `folders`, no ordering metadata, no exclusions. It carries settings, extensions, launch config. Nothing else.

#### The generated file is machine-local

`main.code-workspace` is gitignored, never committed again; fresh machines converge via regeneration, not via git. The mid-rebase conflict-marker state observed 2026-09-19 is the canonical refutation of committing it.

#### Enumeration by discovery, unconditional

One discovery function — depth-1 directories under the workspace root containing `.git` — feeds everything: `status`, the sync verbs' fan-out (`fetch`/`pull`/`push` with `--all` or workspace-root fallback), and workspace emission. No exclusion mechanism exists anywhere: scratch clones join the pane and the sync fan-out unconditionally. The "one code path for enumeration and emit" invariant survives in restated form: one discovery source, zero authored lists.

#### Emission: ordering and naming

- Repos sorted case-insensitively, alphabetically.
- Each repo immediately followed by its worktrees, alphabetical by branch.
- Worktree entries carry `name: "<repo>: <branch>"` — disambiguation everywhere (Explorer, quick-open, search scoping). Prime repos carry no name: their folder name is the repo name.
- Detached-HEAD worktrees render `<repo>: HEAD (detached at abc1234)`.

#### The extension

A small TS extension, living in the prepo repo at `vscode/` (with its own nested `AGENTS.md`). It:

- activates on opening the workspace root as a plain folder (`workspaceContains` the template path) — the fresh-machine bootstrap: it offers to create and open `main.code-workspace`;
- watches the workspace root for repo create/delete and `*/.worktrees/*` for topology changes, debounced;
- shells out to `prepo regenerate-workspace` (a standalone verb, also usable headless) for the at-rest file — all emit logic stays in Python, one code path, testable in scratch repos;
- applies the folder delta at runtime via `updateWorkspaceFolders`, so the pane updates live without waiting for a reload;
- contains no emit logic of its own.

prepo's scope wall holds: prepo never runs the editor; the editor-side component runs prepo.

#### `new`/`drop` re-scope

`new`/`drop` keep exactly their lifecycle contract — idempotent ensure with path-on-stdout, three-variant ref logic (existing branch / remote-only tracking / new), root-checkout collapse, guardrailed compound drop — and lose the workspace-regeneration side-effect. The pane's only maintainers are the extension (live) and the regen verb (at-rest). The regeneration orchestration in `worktrees.py` is deleted; the dual-mount `recorded_path` reconciliation in mutations stays.

### Link semantics: opt-in, above the repos

```
repos/                                  machine-local, above every repository
  main.code-workspace.template         VSCode payload only (settings, extensions)
  main.code-workspace                  prepo-generated, gitignored, machine-local
  repos.link                           prepo: the opt-in linked set
  go.work / .cargo/config.toml         above-repo overlays, when those ecosystems arrive
  placeframe/    zed-box/    capture-tool/    ...
```

`repos.link` lists the linked packages. Listed → local path; unlisted → registry pin. A clone may exist purely for reading without linking. Escape hatches in every direction: edit the file, run `unlink`, or never create it. The file is intent, not state: applied state is a per-checkout cache of a deterministic function — the link rewrite of (HEAD's manifest content, `repos.link`) — validated and re-derived at every mutation point.

### Identity by discovery, not authorship

No identity map is authored. Every package manifest already declares its registry name (`package.json` `name` for UPM/npm, `pyproject.toml` `[project] name` for Python, csproj `PackageId` for NuGet); prepo scans sibling repos and builds the registry-name → local-path translation at runtime. `doctor` validates that registry names are unique across the workspace — the one thing discovery cannot infer. With several checkouts of a sibling, discovery targets the root checkout by default and `status` shows which checkout each link points at; a sibling's post-checkout hook names its consumers when its branch switches, since the link's content silently changes with it. Repo enumeration (workspace transparency) is the same philosophy one level down: directories declare themselves by being git repos; nothing is authored.

### Capability table

| Ecosystem | Native additive override | Clean clone | Clean while linked | Live edits | v1 applier |
|---|---|---|---|---|---|
| Go | `go.work` above repos | ✓ | ✓ | ✓ | deferred |
| Rust | `[patch]` in above-repo `.cargo/config.toml` | ✓ | ✓ | ✓ | deferred |
| npm/pnpm | root workspace manifest | ✓ | ✓ | ✓ | deferred |
| Unity | none (embedded shadowing only) | ✓ | ✓ (git view) | ✓ | git-layer filter pair |
| Python/uv | none (`tool.uv.sources` is pyproject-only) | ✓ | ✓ (git view) | ✓ | git-layer filter pair |

**The law, restated:** {no filesystem indirection, clean-while-linked, live edits, clean single-repo clone} cannot coexist if the override layer must come from the *package manager* — and Unity and uv have none. But the manifests do not live in the package managers; they live in git, and git has a first-class per-clone, additive, optional content-transform layer: clean/smudge filters. The worktree holds a consistent linked world; git's records hold a consistent registry world; the filter pair is the lossless projection between them, and authored changes (residue) flow through both. Every clean-while-linked alternative that *hides authored state* (symlinks, `skip-worktree`, gitignored manifests, embedded copies) remains rejected — the filter hides only prepo's own deterministic plumbing, never content a human authored.

### Git-layer overlay: filters as mechanism, hooks as audit

prepo registers, per checkout, a `filter.prepo` clean/smudge pair (local git config) and path patterns (`.git/info/attributes`) over the two files each ecosystem touches — `Packages/manifest.json` + `packages-lock.json`, `pyproject.toml` + `uv.lock`. Nothing is committed; `git clone` transfers none of it.

- **clean** (worktree → git) strips the link rewrite, deriving the inverse from HEAD (`cat-file`), so status/diff/add see registry content plus residue only. A stateless inverse is wrong the moment HEAD moves (verified).
- **smudge** (git → worktree) applies the link rewrite as files materialize, so checkouts, merges, rebases, and stash pops re-derive the link against each new HEAD. The linked worktree is not dirty from git's perspective, so nothing collides with it — the entire pull/rebase/branch-switch collision class and the textual-merge-of-link-state class disappear.
- **residue** — authored changes in those two files — remains ordinary visible dirt, protected by git's standard dirty-file machinery, committable by plain `git add` (link hunks cannot enter the index at all). The dirty bit becomes pure signal: a dirty manifest means authored dependency changes, nothing else.
- **`required = true`**: a crashed filter is a hard error, never a silent pass-through. The registered command is a self-describing shim — if prepo is missing, git's error names the prepo path and the one-line detach (`git config --remove-section filter.prepo`). Strict mode also fails status/prompt traffic when the filter is broken (clean runs on every status — verified); accepted, and made rare by the update gate below.
- **Hooks audit what filters cannot**: `required` catches crashes, not lies — a filter that runs successfully but computes the wrong transform. Unskippable `post-*` hooks assert content invariants after every mutation (worktree linked wherever `repos.link` says linked; staged content equals HEAD + residue), pre-commit warns on unstaged residue in the link files, and pre-push guards leakage.
- **Reconciliation**: `link`/`unlink` rewrite the two files (apply or strip link hunks, always preserving residue) and no-op `git add` them to refresh the index stat cache — required because git's dirty check short-circuits on raw size mismatch (verified) and because uv/Unity rewrite the lock files themselves; post-merge/post-checkout hooks re-refresh after topology changes. `unlink` never runs installs: the venv self-heals via `uv run`'s provenance validation, the editor re-resolves on open.
- **Failure shapes**: filter config absent (fresh machine, detached clone) → linked bytes show as ordinary visible dirt, the superseded bracketed mode's steady state, fully recoverable; prepo missing under live config → loud self-naming git error; buggy filter → git bricked until rollback (deliberate: structurally impossible to fail silently).
- **`prepo update` self-test**: new filter scripts run against a fixture corpus of real manifests/locks in scratch repos before an atomic swap; last-known-good is kept alongside. `prepo detach` unlinks and uninjects cleanly.

If the remaining gates (Open parameters) fail — the HEAD-read deadlock and the merge/stash content shapes — the design falls back to the superseded bracketed ephemeral-rewrite mode (Discarded alternatives): correct, but dirty-while-linked.

### Visibility: where the state explains itself

Filters cannot message (verified: clean fires on every status; stderr would spam prompt and IDE traffic) and aliases cannot shadow builtins, so awareness lives in three places: mutation hooks print one-liners (`prepo: 2 links reconciled against new HEAD`), a shell-prompt segment shows linked packages whenever cwd is a linked checkout, and `prepo status` renders the per-checkout application matrix (which repos, which checkouts, which sibling branches, residue present or not).

### Unity applier

`link` rewrites the listed dependencies to `file:` refs into sibling repos and refreshes the index; live edits flow both ways, nothing is copied, the editor recompiles as before. Git's records always carry the registry-shaped manifest and lock — never gitignored; lock determinism (why `lock-unity` exists) stays intact in every clone, linked or not. Fallback: no linking at all — registry pins + `bump`.

### uv applier

Same filter pair over `pyproject.toml` + `uv.lock`: at rest a PyPI pin; the linked worktree carries the `tool.uv.sources` path entry and path-sourced lock; clean strips both back to the registry shape. The venv needs no command at either boundary (provenance validation self-heals both directions), keeping prepo inside its never-runs-installs wall.

### bump

Moves a repo's pins to a chosen published version — latest stable or newest `-dev.<run-id>` — resolved by registry query. This is the discovery path implied by immutable versions, and the standard answer to accepted-stale pins: bumping is always the consuming repo's prerogative; automation for the bump chore is an open parameter.

## Discarded alternatives

- **Standalone extension repo (`prepo-vscode`)** (initial structure, 2026-09-19): convention-mimicry ("the bashrun standalone-tool model"), not a derived requirement. The extension cannot function without prepo installed, the toolchain-collision concern is already handled by defaults (ruff/pytest exclude `node_modules`; basedpyright and the wheel target only `src/`), and package-discovery "pollution" was already the status quo via the sibling repo — inert because links are `repos.link`-gated. Dominated by `vscode/` in the prepo repo. Would be revisited only if the extension were ever published for consumers who don't have prepo.

- **Committed generated workspace file** (the status quo until 2026-09-19): machine-local topology under version control; observed producing conflict markers that left the pane unparseable mid-rebase. Rejected for gitignored machine-local output.
- **Template exclusion/ordering lists** (pinned-minus-excluded enumeration): keeps authored member state in the template and the Pin-X chore alive. Rejected for unconditional discovery.
- **Bare branch-name worktree titles**: adjacency disambiguates only inside the Explorer pane; quick-open, search scoping, and standalone window titles lose the repo. Rejected against the disambiguation-everywhere requirement.
- **Regeneration via daemon or shell prompt**: the only component that can apply pane changes without a reload is the extension; a daemon still pays the reload prompt and duplicates the watcher. Dominated by the extension.
- **Symlinked embedded packages (Unity)**: was the initial candidate — a gitignored symlink under `Packages/` shadows the registry entry with no manifest writes and clean-while-linked semantics. Rejected: filesystem indirection is the wrong class of mechanism — OS-hostile, invisible to tooling, and exactly the footgun category this design refuses.
- **`git update-index --skip-worktree` hiding**: makes git report clean while linked by hiding the manifest from the index — trades visible, bracketed dirt for invisible dirt; upstream manifest changes during a pull collide confusingly. Rejected.
- **Gitignored generated Unity manifest + committed template**: a fresh clone then lacks a required build file — fails fresh-clone autonomy outright.
- **Presence-as-intent linking** (link whatever is cloned): rejected in favor of the explicit `repos.link` — clones exist for reading; intent must be explicit, inspectable, and stable per developer.
- **Authored identity map file**: rejected — package manifests already declare their registry names; runtime discovery plus a uniqueness check replaces authorship entirely.
- **Floating `dev` dist-tag as the consumption interface**: rejected — mutable pointers; immutable versions only. (The inert dist-tag remains as npm publish plumbing, never as an interface.)
- **Committed uv path sources**: machine-specific paths in version control break every other machine and CI — the uv maintainers' own position; path sources are acceptable only as prepo-managed ephemeral state.
- **Venv overlay (uv)**: editables installed over the locked venv, zero git-visible change — evicted by `uv run` and `uv sync --inexact` provenance validation (verified above); survivable only for packages absent from the lock, which fresh-clone autonomy forbids anyway.
- **`link --embed`/`harvest` (Unity)**: a gitignored embedded copy under `Packages/` avoids the manifest write but puts edits in unprotectable space, forks the edit location into a drifting copy, and adds a second Unity mechanism. Dominated by `file:` linking (itself live-editable with editor recompiles) once the hook is standard.
- **Git-source at-rest pins (uv)**: zero infrastructure and private-safe, but every bump is commit churn in a committed file plus a relock, and the dev channel cannot serve immutable `-dev` versions through git at all.
- **Bracketed ephemeral-rewrite as the primary mode** (the previous design): link rewrites the two committed files, unlink git-restores them. Correct and fully derivable, but dirty-while-linked — which burns the dirty bit's meaning in exactly the files where authored changes matter, collides with pulls/rebases/branch switches, and makes every commit that touches dependencies hunk surgery. Superseded by the git-layer filter overlay; retained as the fallback if its remaining gates fail.
- **Filter stderr / alias decoration of git output**: verified dead ends — clean fires on every status (stderr would spam prompts and IDEs), and git aliases cannot shadow builtins.
