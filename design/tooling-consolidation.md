# Tooling consolidation — the deduplication program

## Scope

Thread 5 of the polyrepo initiative ([index](polyrepo.md)), born from thread 4's duplication audit: eliminate first-party code and config duplication **org-wide**, not just what the capture-tool extraction would have introduced. Operator ruling 2026-09-21: **deduplication maximalism** — already-existing duplication is fair game regardless of refactor invasiveness or blast radius. Thread 4 (the capture-tool extraction) is **parked behind this program**; it resumes only after this checklist completes. Siblings: [thread 4, the extraction](repo-extraction.md) and its [duplication audit + reconnaissance ground truth](repo-extraction.md).

## Problem

The org's tool tier grew per-need, and the seams show: `ruff.toml` is mirrored in 8 repos with 8 different hashes (silent drift already happened), every tool repo carries a near-identical ~40-line `ci.yml`, placeframe's `unity-build.yml` is shared infrastructure hosted in a consumer repo, and the first capture-tool bootstrap attempt copied `lock_python.py`, the codegen orchestrator, and preflight internals verbatim rather than consuming shared code. The audit's ruling: no copied first-party logic anywhere; shared code moves to domain homes; **new repos only where no existing home fits**.

## Decisions (operator, 2026-09-21)

- **The `-devkit` family**: `python-devkit`, `unity-devkit`, `docker-devkit`, `release-devkit` — repo name == PyPI distribution name, 1:1. Plain `*-toolkit` is impossible (`python-toolkit` and `release-toolkit` are taken); `kit-*` prefix rejected as word-order-awkward. All four verified 404 with no ultranormalized twins; **registration is provisional until the pending-publisher probe passes** (a 404 cannot see registered-but-release-less projects, the secret prohibited list, or Test-PyPI divergence).
- **Renames now, while cheap**: everything is ≤0.1.x with ~one consumer each and no stable releases. GitHub renames happen in place (redirects preserve history); PyPI gets new projects plus terminal deprecation releases on the old names (the logger-conf pattern).
- **`release-devkit` stays whole** — no per-ecosystem split. Its content is registry/git machinery (ledger, plan, feeds, releases, PRs, artifacts) organized by *registry* (nuget/npm/pypi/ghcr), not by unity/python; `dependency_pins` cross ecosystems within one release event, so a split would re-merge via a shared ledger. Its own recorded ruling already refuses per-ecosystem splits; the audit confirms it. `mirror-images` **stays**: populating the org mirror under org credentials from `publish-config.json` is a publication act — the pre-build timing is CI scheduling, not domain.
- **`ci-devkit`, the CI runner floor (operator ruling 2026-09-21)**: the extraction of `ci_step` + runner provisioning into python-devkit was corrected mid-flight — those modules are not Python-domain but the runner floor every devkit builds on (the tell: unity-devkit would have depended on a *python-lifecycle* package just for `configure_git`). A fifth devkit owns them: `bashrun` → `ci-devkit` → domain devkits is the layering. The floor also took unity-devkit's `git_tags.py` (generic tag primitives — release-devkit's `ledger.py` was a near-duplicate and now converges onto it, keeping only the stable-version filter) and `cache.py` (a generic tar+zstd OCI artifact cache with non-Unity consumers; media type rebranded `vnd.ci-devkit.cache.v1+zstd`, restore-safe since pulls don't filter on it). `install_dotnet`/`install_node` live here so a future `node-devkit` consumes the floor rather than a python package. python-devkit stays pure-python (`lock-python`, preflight runner, ruff canonical, python check workflow) and **does not publish until its first real content lands** — its accidentally-published `0.1.0` (pushed during the wave-4 window before the rework, carrying the floor content) is unconsumed and unconsumable; nothing pins it, and the strip commit is held until item 6 so no empty release follows it.
- **`logger-conf` and `bashrun` stay standalone**. Kits own cross-repo tooling consumed at dev/CI time; runtime libraries stay independent distributions (absorbing logger-conf would drag the dev-CLI toolchain into every service image and couple service locks to tooling bumps). bashrun is a dependency *of* the kits — a package cannot absorb its own dependency. No cycle exists either way (bashrun has zero runtime deps; verified).
- **Observability = stock consumption, no new repo** (operator ruling 2026-09-22, superseding the `observability-images` plan the day before creation): loki/alloy/grafana drop the wrapper images entirely — digest-pinned stock mirror refs + compose `configs:` (file-sourced locally, content-inlined into the published OCI bundle, flat-shipped beside the box's rig compose). The wrappers were two COPY lines over 134 lines of YAML; the OCI-include consumer (Make-it-Sing) is served by the configs mechanism, not by baked images. Full plan + probe evidence: [observability-stock-consumption.md](observability-stock-consumption.md). `config.alloy` returns to an accepted one-file mirror (placeframe + capture repo) under the original third-consumer revisit trigger.
- **openapi-client-codegen stays as-is** (name and repo): a domain tool in the same class as bashrun, not python-repo-lifecycle tooling. It gains the project orchestrator verb (Phase 3).
- **Preflight = the fixed Python battery, not a general-purpose check runner (operator ruling 2026-09-22, overruling Phase 5's "adoption is moot" resolution the same day)**: python-devkit's preflight runs one fixed battery — the things true of every healthy org Python repo — so CI and local runs become the same command everywhere. The shipped shape (a generic `CommandCheck`/`GeneratedCheck` list) was preflight co-opted by placeframe's specifics: codegen staleness is a repo concern (this repo's generators reproducing its tree), not Python-domain, and the generic runner earned exactly one consumer. Battery members: sync, ruff check, ruff format check, basedpyright, deptry, pytest, lock staleness, ruff drift. The public surface is toggles only; repo-specific checks compose locally around the battery, never inside python-devkit.
- **Workflow shape (grounded in OIDC research, 2026-09-21)**: PyPI hard-blocks reusable workflows as trusted publishers (warehouse#11096, open — the registrar matches the caller-repo `repository` claim against the reusable workflow's `job_workflow_ref`); npm binds the caller's top-level workflow filename and npm staff advise against `workflow_call` publishing; npm's one-publisher-per-package limit is now 10 (Sept 2026). Therefore: **reusable workflows for everything non-publishing** (check CI → python-devkit repo; `unity-build.yml` → unity-devkit repo — GITHUB_TOKEN cache pushes already work cross-repo, Make-it-Sing proves it), and **release-devkit ships publish composite actions** (composite steps run inside the caller's job, so OIDC identity stays local under both registries), with each consumer keeping a thin top-level publish workflow whose dedicated publish job runs them. No `setup-uv` composite anywhere — reusable workflows must be self-contained, so they inline `astral-sh/setup-uv@v7`.

## Discarded alternatives

- **`observability-images` repo**: discarded 2026-09-22, before creation — probe findings + rationale recorded in [observability-stock-consumption.md](observability-stock-consumption.md)'s own discarded-alternatives section (the naive bind-mount switch and keep-the-wrappers options live there too).
- **Per-ecosystem split of release-kit** (unity feeds → unity-devkit, PyPI feed → python-devkit): refused — feeds split by registry, not consumer ecosystem; `dependency_pins` cross ecosystems in one release event; a split re-merges via the shared ledger. release-kit's own doc records the same ruling.
- **Absorbing logger-conf (or bashrun) into python-devkit**: runtime-library vs dev-tooling planes; services must not inherit the dev CLI toolchain; a package cannot absorb its own dependency.
- **One org-CI repo hosting all reusable workflows**: loses domain locality; publish must stay local-thin anyway (OIDC), so the mega-repo buys nothing the domain homes don't.
- **`mirror-images` → docker-devkit**: retracted — mirror population is a release/registry act.
- **Plain `*-toolkit` family**: `python-toolkit` and `release-toolkit` are taken on PyPI.
- **`kit-*` prefix family**: available but word-order-awkward.
- **No renames (add only python-devkit)**: forgoes the uniform family; the cheap window (≤0.1.x, ~one consumer each, no stable releases) closes at the first stable release — operator preferred consistency.
- **ruff config via venv-path `extends`**: fragile path coupling into `.venv`; sync-verb + drift gate is the maximalist-compliant mechanism given ruff has no remote extends.
- **Adopting ruff-sync (Kilo59) instead of the in-house verb**: rejected 2026-09-21 — wrong transport (remote URL/git ref, mutable by default, vs the pinned PyPI package that versions verb and canonical on one axis), wrong merge model (tomlkit semantic merge into a single file vs byte-identical base + extend layer with a trivial drift check and visible provenance), no layer-shape guard, and a single-maintainer dependency (6 stars) sitting inside ten CI gates. Architecture research verdict: ruff has no native remote/package extends as of 0.16.8 — astral-sh/ruff#12352 open 2+ years `needs-design`, #13245 closed `not_planned`, #22886 filed Jan 2026 — and every viable pattern (copy+gate, templating, bot PRs, submodule, env-var, CI-fetch) was evaluated; all but copy+gate fail the IDE-discovery, Windows, pinning, or air-gap constraints, and copy+gate is exactly what was built. Exit trigger: if ruff ships #12352 with a pinning story, delete the verb, keep the layers, repoint `extend`.
