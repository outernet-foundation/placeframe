# Polyrepo redesign: publishing, standing channels, repo boundaries, prepo

## Scope

Three workstreams under one design:

1. **Publishing** — own the UPM derivation, dual-feed publish (nuget + npm), a public standing dev channel. This is the original package-publishing redesign; its forensic basis is retained below.
2. **Repo boundaries** — extract the phone-side capture tool and the ZED box appliance into standalone repos; their consumption of placeframe packages changes from intra-repo `file:` refs to cross-repo registry refs.
3. **prepo** — expand pgit (rename pending) into the polyrepo workbench: an opt-in local dependency overlay that preserves single-repo autonomy.

The file keeps its original path (`package-publishing-redesign.md`) so existing ticket blob-links survive; its scope is now the umbrella. Ordering among the three workstreams is deliberately unstated — sequencing is decided when execution starts, not here.

## Problem

Publishing:

1. A **public, standing dev channel**: every green `dev` push produces complete, installable, **immutable** bleeding-edge packages for every repo; `main` continues to produce stable releases through the release flow.
2. The generated C# clients stay **one authored package per client**, consumable by both Unity applications and non-Unity .NET applications.

UnityNuGet blocks requirement 1 structurally, and the current pipeline carries several latent defects discovered during forensics (below).

Boundaries:

3. The capture tool and the ZED appliance become standalone repos. Cross-repo consumption is registry consumption — which makes workstream 1 load-bearing rather than cosmetic: a broken publish no longer costs external visibility, it blocks the other repos' development loops.

Local iteration:

4. A developer iterating across repos must be able to swap any registry dependency for a local, live-editable sibling checkout — per developer, without git noise at rest, and without breaking the guarantee that **any single repo clones, builds, and stays `git status`-clean with no knowledge of prepo**.

## Ground truth (verified 2026-09-18)

### UnityNuGet mechanics

- Ingestion is **stable-only**, and this is in the *code*, not just public-service policy: prerelease support was requested and declined upstream (xoofx/UnityNuGet#104) citing storage pollution and NuGet→npm/UPM semver remap mess. No prerelease version can ever flow through the public mirror, and a self-hosted stock instance inherits the same filter.
- Scan cadence: the registry re-scans nuget.org every **10 minutes** (`UpdateInterval`); OpenUPM's uplink syncs **hourly**.
- The curated list (`registry.json`) requires every transitive dependency to be explicitly listed, and new curated entries only appear after the maintainers' next Docker image release.

### Why UnityNuGet was adopted (T71, 2026-03-04)

The T71 plan and ticket record the decision: publish `vps`/`-arfoundation`/`-magicleap` to npmjs, route clients through UnityNuGet because they were "already published to NuGet and available via the UnityNuGet registry" — i.e. avoid duplicate publishing and get dependency derivation for free. The free-derivation premise had a concrete basis: the generated source packages carried **no `dependencies` block** (they still don't), while the UnityNuGet DLL repack derived the graph (`newtonsoft.json`, `polly`, `jsonsubtypes`) from the nuspec. The stable-only premise was harmless in a stable-only world; the dev-channel requirement breaks it.

### Present defects in the pipeline

- **api-client publish landmine**: `openapi-clientgen`'s `unity.py` strips the generated `.csproj` (to keep IDE `bin/`/`obj/` out of the UPM package); the last `Run generate-clients` (7ccbd750, 2026-06-05) deleted `PlaceframeApiClient.csproj`, but `publish_packages.py` still runs `dotnet pack` in that directory. The next stable release fails. `dev` already carries generate-clients changes since `placeframe-api-client-v0.1.7`, so the very next release hits it.
- **Zed client lineage fork** (c4dc285e, 2026-04-28, "Containerize ZED capture"): the `zed` project entry became `docker/zed-capture`; generated identity changed `PlaceframeZedClient` → `PlaceframeZedCaptureClient`, output dir `zed-client/` → `zed-capture-client/`; apps were repointed in the same commit. The cleanup never happened:
  - `packages/generated/csharp/zed-client/` is frozen (last touched 2026-05-03, regenerated by nothing — absent from `build/openapi-projects.json`) yet still wired into `publish_packages.py`/`create_release.py`.
  - It was even published once post-mortem: `placeframe-zed-client-v0.1.5` (2026-05-13), triggered by a design-notes doc move inside the dead tree tripping the path-diff change detection.
  - nuget.org serves `PlaceframeZedClient` 0.1.0–0.1.5 (an April-era API surface) and the UnityNuGet mirror serves it too, while the live successor `PlaceframeZedCaptureClient` — regenerated on every `generate-clients`, consumed by CaptureTool via `file:` — is published nowhere.
- **`org.outernet.placeframe.auth`** is a real UPM package (consumed by CaptureTool via `file:`) missing from the publish set entirely.
- **`org.outernet.logging`** likewise: consumed by CaptureTool via `file:`, version `0.0.0-local`, in no publish set anywhere.
- `com.placeframe.vps@1.0.0` is an orphaned pre-rename relic still live on npm (published 2026-03-05, nine minutes before the scope was renamed to `org.outernet.placeframe`).

### Ecosystem override capabilities

How each ecosystem supports "registry by default, local path for the packages under iteration" — per official docs and tracker threads:

- **uv**: `[tool.uv.sources]` is the only source-override mechanism and it must live in `pyproject.toml` — not `uv.toml`, not env vars, not CLI flags; the maintainers have declined otherwise on lockfile-coherence grounds ("sources outside the pyproject would invalidate the lockfile"; astral-sh/uv #6772, #11632, #12013, #15895). The lock records path sources while they are active.
- **Cargo**: `[patch]` may live in `.cargo/config.toml`, which cargo discovers by walking up parent directories; the Cargo Book states config-file patching is "generally only appropriate when the patch section is automatically generated by an external build tool," and relative paths resolve from the config file. An overlay above all checkouts is therefore first-class.
- **Go**: `go.work` is per-developer, discovered by walking up, and the workspace design proposal both says not to commit it and anticipates that "the creation of the file can be automated by an external tool that scans for all the go.mod files recursively." CI runs with `GOWORK=off`.
- **Unity/UPM**: no per-user or local override layer exists (Unity staff confirmation on the 2021 `manifest.local.json` request: "There's nothing in place to allow what you want to do here"). The one structural override: a package embedded under the project's `Packages/` directory shadows the same-name registry entry. Separately, `file:` and git dependencies are treated by the SAT solver as overriding any version constraint, and `file:` paths may traverse outside the project.
- **npm**: dist-tags are floating pointers by construction; Unity's resolver has no dist-tag concept and its version ranges never jump a stable pin onto a prerelease (exact prerelease pins do resolve).

## Design

### 1. Publishing

#### Derivation moves in-house

```
openapi-clientgen (placeframe)              openapi-clientgen (zed repo)
  └─ emits UPM source package + csproj        └─ emits UPM source package + csproj
        │                                           │
  publication machinery repo (shared)        publication machinery repo (shared)
        ├─ dotnet pack ──► nuget.org                 ├─ dotnet pack ──► nuget.org
        └─ npm publish ──► registry.npmjs.org        └─ npm publish ──► registry.npmjs.org

Unity projects: scoped registry npmjs (org.outernet.*) + scoped registry UnityNuGet (third-party org.nuget.*)
```

The nuget package remains the general-purpose C# artifact. The UPM tarball is a **derived build output of the same generated tree** — never independently authored, never separately versioned. "Publish once" is preserved; what changes is that the Unity variant is derived by our pipeline instead of a third-party service that cannot carry prereleases.

#### Identity

- npm: `org.outernet.placeframe.apiclient`, `org.outernet.placeframe.zedcaptureclient` (matches the existing `org.outernet.placeframe` / `-.arfoundation` / `-.magicleap` scope).
- Assembly names (`PlaceframeApiClient`, `PlaceframeZedCaptureClient`) are unchanged, so consumer `.asmdef` references survive the rename untouched.
- The UnityNuGet scoped registry stays in consumer manifests **for third-party packages only** (`org.nuget.polly`, `org.nuget.r3`, `org.nuget.mathnet.numerics`, …).

#### Source package, not DLL repack

The published UPM artifact is the generated **source** package (asmdef), identical in shape to what in-repo projects consume via `file:` refs today. Rationale:

- Artifact unification: in-repo (`file:`) and external (registry) consumers get the same thing — one consumption contract, no drift.
- Zero conversion machinery: no nupkg→UPM repack step to own or fork (that machinery is what this design deletes).
- Consumers can read and debug the source.

Accepted tradeoff: the consumer's Unity compiler compiles the client, so the generated code's language level sets an implicit Unity floor. Guard: keep the patched generator templates at C# 8/9 (`csc.rsp` already enables nullable annotations, implying a C# 8 floor). We control both the templates and the Unity versions in use, so the exposure is bounded.

#### Emitted dependencies

`package.json` gains a `dependencies` block — closing the one concrete gap that made UnityNuGet feel cleaner in T71:

- `com.unity.nuget.newtonsoft-json` — the Unity-blessed Newtonsoft. A 1:1 nuspec mapping (`org.nuget.newtonsoft.json`, what the UnityNuGet repack declares) collides with the Unity-provided assembly most projects already carry.
- `org.nuget.polly`, `org.nuget.jsonsubtypes` — third-party, resolved via the UnityNuGet scoped registry.
- Version **ranges**, not exact pins, so consumer manifests already carrying newer minors don't conflict.

#### Versioning

- Committed `package.json` versions are permanently `0.0.0-local`; the real version is patched in ephemerally at publish time and never committed (same invariant as the existing Unity packages).
- Per-package git tags (`{package}-v{semver}`) remain the single version ledger; both feeds publish the **same semver** for the same release.
- `zed-capture-client` starts a fresh ledger at 0.1.0 in the zed repo (its predecessor's `placeframe-zed-client-v*` tags stay as historical record in placeframe).

#### Publish set

| Package | nuget.org | npmjs (UPM) | Published from |
|---|---|---|---|
| placeframe-core | — | ✅ existing | placeframe |
| placeframe-arfoundation | — | ✅ existing | placeframe |
| placeframe-magicleap | — | ✅ existing | placeframe |
| placeframe-auth | — | ➕ new | placeframe |
| placeframe-logging (`org.outernet.logging`) | — | ➕ new | placeframe |
| placeframe-api-client | ✅ existing | ➕ new | placeframe |
| placeframe-zed-capture-client | ➕ new | ➕ new | zed repo |

#### Publication machinery

A new standalone repo (sibling of `unity-buildkit` / `stack-lifecycle` / `bashrun` / `openapi-clientgen`; name open) owns: the publish pipeline, the per-package tag ledger and path-diff change detection, ephemeral version patching, `mirror-images` and the digest-pinned mirror scan, and release orchestration. placeframe, the zed repo, and the capture-tool repo all consume it. Per-repo copies of this machinery are refused — it is written once.

#### Dev channel

- `main` → stable, via the existing release flow (release PRs + tags; the tag space is the stable version ledger).
- `dev` → every green push publishes **immutable** `-dev.<run-id>` prereleases of every changed package (path-diff detection as today) to both feeds.
- npm requires a non-`latest` dist-tag to publish a prerelease without moving `latest`; a single inert `dev` dist-tag exists as that plumbing only. **The version list is the interface**: consumers pin exact immutable versions; discovery is a registry query, wrapped by `prepo bump`. Floating-tag consumption (`pkg@dev`) is rejected.
- Unity consumes dev builds as exact version pins; its resolver never auto-jumps a stable range onto a prerelease.
- Dev publishes **never create git tags**.
- No standing services: both registries are public CDNs; publishing is a CI job.

### 2. Repo boundaries

#### Extraction

| New repo | Takes | Publishes |
|---|---|---|
| capture-tool (name open) | `apps/CaptureTool/`, the `capture-tool-v*` tag prefix, `unity-build.json`, the AOA Java/OkHttp client + handler, the log relays, the `install --project CaptureTool` flow | APKs |
| zed appliance (name open) | `docker/zed-capture/`, `docker/aoa-bridge/`, `docker/aoa-gateway/`, box `loki`/`alloy` configs, `compose.rig.yml`, the zed targets of `compose.zed.bake.yml`, `placeframe-zed.service`, `wait_for_zed_camera.py`, `install-zed` (`scripts/src/scripts/install_zed/`), zed-capture-client generation (openapi-clientgen as a library) | `PlaceframeZedCaptureClient` (nuget + npm), box images (own GHCR namespace) |

placeframe keeps the server stack, the UPM SDK (`Core`, `ARFoundation`, `MagicLeap`, `Auth`, `Logging`), api-client generation, and MapRegistrationTool as an in-repo consumer — the `file:` consumption path stays exercised where it remains intra-repo. The top-level `zed/` tree is dead (its `src/` contains only `__pycache__`): delete it, do not move it.

#### Cross-repo contracts

Four contracts become inter-repo. Each gets one authoritative home, referenced — never duplicated — by both sides' agent docs:

1. **Capture tar** (`rig*/frames.csv` + stereo JPEGs + factory calibration) — box → placeframe reconstructor.
2. **zed-capture REST API** — box → phone. The committed `openapi.json` is the machine-checkable artifact and the compat gate; the phone pins a `zedcaptureclient` version.
3. **AOA transport** (h2c prior-knowledge over the accessory FD, bridge forwarding to `127.0.0.1:9000`) — phone ↔ box.
4. **Log drain** (box-clock semantics, restamp at the push boundary) — box → phone → backend.

#### Fresh-clone autonomy (hard requirement)

Every repo, cloned alone, with the standard toolchain: builds green, `git status` clean, prepo unknown to the cloner. CI is the no-prepo user — it is a fresh lone clone by construction, so autonomy holds exactly when appliers never run in CI. An optional per-repo committed pre-commit hook rejects `file:` refs escaping the repo and unexpected package dirs; it is inert for anyone who never links, and is belt-and-suspenders — the primary safety is bracketing and visibility (§3).

### 3. prepo

#### Placement and scope

pgit expands (rename pending; `prepo` is a placeholder) from git porcelain to polyrepo workbench. The existing six verbs are unchanged. New cohort: `link`, `unlink`, `bump`, `doctor`; `status` gains overlay visibility. The scope wall moves from "language-agnostic, no environment provisioning" to **language-aware, build-agnostic**: prepo reads and writes package-manager manifests; it never runs builds, installs, or editors (`uv sync`, `npm install`, Unity remain the caller's commands). This keeps the tool testable with scratch repos and keeps build semantics inside each ecosystem's own tooling.

#### Link semantics: opt-in, above the repos

```
repos/                                  machine-local, above every repository
  main.code-workspace.template         pgit (existing)
  repos.link                           prepo: the opt-in linked set
  go.work / .cargo/config.toml         above-repo overlays, when those ecosystems arrive
  placeframe/    zed-box/    capture-tool/    ...
```

`repos.link` lists the linked packages. Listed → local path; unlisted → registry pin. A clone may exist purely for reading without linking. Escape hatches in every direction: edit the file, run `unlink`, or never create it.

#### Identity by discovery, not authorship

No identity map is authored. Every package manifest already declares its registry name (`package.json` `name` for UPM/npm, `pyproject.toml` `[project] name` for Python, csproj `PackageId` for NuGet); prepo scans sibling repos and builds the registry-name → local-path translation at runtime. `doctor` validates that registry names are unique across the workspace — the one thing discovery cannot infer.

#### Capability table

| Ecosystem | Native additive override | Clean clone | Clean while linked | Live edits | v1 applier |
|---|---|---|---|---|---|
| Go | `go.work` above repos | ✓ | ✓ | ✓ | deferred |
| Rust | `[patch]` in above-repo `.cargo/config.toml` | ✓ | ✓ | ✓ | deferred |
| npm/pnpm | root workspace manifest | ✓ | ✓ | ✓ | deferred |
| Unity | none (embedded shadowing only) | ✓ | — | ✓ | manifest `file:` rewrite |
| Python/uv | none (`tool.uv.sources` is pyproject-only) | ✓ | — | ✓ | venv overlay, else pyproject patch |

**The law:** absent a native *additive, optional* override layer, {no filesystem indirection, never-dirty-while-linked, live edits, clean single-repo clone} cannot hold simultaneously. Unity and uv lack such a layer (verified above); their appliers therefore run in **bracketed ephemeral-rewrite mode** — dirty only between `link` and `unlink`, clean at rest, always restorable from git, visible in `status`. This is the cost of those ecosystems' missing layer, stated in the table rather than papered over.

#### Unity applier

`link` rewrites the listed dependencies in `Packages/manifest.json` from version pins to `file:` refs into sibling repos — the intra-monorepo workflow, generalized; live edits flow in both directions, nothing is copied. `unlink` restores from git. Lock file (`packages-lock.json`): restore on unlink, or gitignore in app projects (open). Opt-in variant (open): `link --embed` copies the package into `Packages/` (gitignored) for deep iteration with instant recompiles — the canonical UPM embedded-dev workflow — and `harvest` syncs edits back and unlinks. Always-available fallback: no linking at all — registry pins + `bump`.

#### uv applier

Candidate: **venv overlay** — `uv sync --inexact`, then `uv pip install -e` for each linked sibling package; `unlink` is a plain `uv sync`, which resets the venv to locked state. Zero git-visible change at any point; the overlay lives entirely in gitignored venv state. Prototype gate: whether `uv run`'s auto-sync evicts manually-installed editables. If it does, uv falls to the same bracketed ephemeral patch as Unity (`pyproject.toml` + lock, restored on unlink).

#### bump

Moves a repo's pins to a chosen published version — latest stable or newest `-dev.<run-id>` — resolved by registry query. This is the discovery path implied by immutable versions, and the standard answer to accepted-stale pins: bumping is always the consuming repo's prerogative; automation for the bump chore is an open parameter.

## Change set

### openapi-clientgen

1. `unity.py`: stop deleting the `.csproj` (it is the nuget pack input); instead redirect build output outside the package dir (`BaseIntermediateOutputPath` et al.) so IDE builds stop writing `bin/`/`obj/` into the UPM package — which was the original reason for the strip.
2. `unity.py`: emit the `dependencies` block, `version: "0.0.0-local"`, `license` + `repository` fields; make the npm scope configurable, producing `org.outernet.placeframe.*` names.
3. Patched C# templates: keep the csproj pack-correct (`PlaceframeZedCaptureClient.csproj`, which still survives in-tree, is the reference shape).
4. The zed repo consumes openapi-clientgen as a library for zed-capture-client generation and publishing; placeframe's `generate-clients` drops the zed project entry at cutover.

### placeframe

5. Publish/tag/release logic migrates to the publication-machinery repo; placeframe retains package configuration only.
6. Core `package.json`: dependency `org.nuget.placeframeapiclient` → `org.outernet.placeframe.apiclient`; `org.outernet.logging` joins the publish set under the same `0.0.0-local` invariant.
7. Regen: `uv run generate-clients` → canonical `Run generate-clients` commit.
8. Extraction proceeds per the boundary table; dead trees (`zed/`, `packages/generated/csharp/zed-client/`) are deleted at cutover, not moved.
9. Docs: `build/AGENTS.md` codegen section; `AGENTS.md` environment-notes mount list; README Unity-consumer docs (two scoped registries); each side's agent doc references the four contract homes.

### prepo

10. Rename pgit → placeholder `prepo`: entry point, all agent-doc references, and the scope-wall statement (spec-first — the doc rewrite precedes the new verbs).
11. `repos.link` parsing, the discovery scan, and `doctor` uniqueness validation.
12. Unity applier (bracketed manifest rewrite) + lock handling; decide the `--embed`/`harvest` variant.
13. uv applier prototype: establish `uv run` auto-sync eviction behavior; ship venv overlay or ephemeral patch accordingly.
14. `bump` + the `status` overlay column.

### Cutover and retirements

15. First dual-publish under one version (`0.1.8` for api-client; fresh `0.1.0` for zed-capture-client from the zed repo; core release carries the repointed dependency).
16. UnityNuGet curated-list removal PR: the `PlaceframeApiClient` and `PlaceframeZedClient` entries. Not optional hygiene — the mirror tracks nuget.org forever, so without removal every future stable keeps shadow-publishing under the dead `org.nuget.*` identities. A brief dual-identity window during the maintainer's merge latency is accepted.
17. Deprecate `PlaceframeZedClient` 0.1.x on nuget.org with a pointer to the successor; deprecate the `com.placeframe.vps@1.0.0` npm relic.
18. Phase 2 (after one real dual-publish verified end to end): turn on the dev-channel job publishing on every green `dev` push.

## Discarded alternatives

Publishing (original):

- **Self-host a public UnityNuGet**: buys the same one-authored-package property but requires a permanent public HTTPS service *plus* a maintained fork (prerelease support doesn't exist in stock code) — renting the problem instead of solving it.
- **`UnityNuGet.Tool` in CI as the converter**: inherits the same stable-only filter, so it needs patching anyway, and it outputs the DLL-repack artifact shape.
- **Stable-formatted burn versions (99.x) through the public mirror**: a dev build would become "latest" for every consumer of the package page and Unity's Package Manager — exactly the pollution upstream declined prereleases to avoid.
- **Consume the nuget package in Unity via NuGetForUnity**: most literally one package/one feed, but it drops the client out of the UPM dependency graph (core can't declare it) and restores a duplicate-Newtonsoft conflict with `com.unity.nuget.newtonsoft-json`.
- **DLL repack as the published artifact**: keeps the conversion machinery this design deletes and forks the consumption contract into two artifact shapes (in-repo source vs external DLL).

prepo / overlay:

- **Symlinked embedded packages (Unity)**: was the initial candidate — a gitignored symlink under `Packages/` shadows the registry entry with no manifest writes and clean-while-linked semantics. Rejected: filesystem indirection is the wrong class of mechanism — OS-hostile, invisible to tooling, and exactly the footgun category this design refuses.
- **`git update-index --skip-worktree` hiding**: makes git report clean while linked by hiding the manifest from the index — trades visible, bracketed dirt for invisible dirt; upstream manifest changes during a pull collide confusingly. Rejected.
- **Gitignored generated Unity manifest + committed template**: a fresh clone then lacks a required build file — fails fresh-clone autonomy outright.
- **Presence-as-intent linking** (link whatever is cloned): rejected in favor of the explicit `repos.link` — clones exist for reading; intent must be explicit, inspectable, and stable per developer.
- **Authored identity map file**: rejected — package manifests already declare their registry names; runtime discovery plus a uniqueness check replaces authorship entirely.
- **Floating `dev` dist-tag as the consumption interface**: rejected — mutable pointers; immutable versions only. (The inert dist-tag remains as npm publish plumbing, never as an interface.)
- **Committed uv path sources**: machine-specific paths in version control break every other machine and CI — the uv maintainers' own position; path sources are acceptable only as prepo-managed ephemeral state.

## Open parameters

None of these block the design; each is decided at execution time.

- Workstream ordering (deliberately punted).
- Names: both new repos, prepo's final name, the zed repo's npm scope, GHCR image namespaces, the `repos.link` filename.
- Publication-machinery repo boundaries (standalone vs. `unity-buildkit` extension).
- Phone↔box compat policy (N-1 vs. paired versions; field upgrade ordering); authoritative homes for the four cross-repo contracts.
- Release orchestration across repos (independent cadences vs. coordinated train); release-PR scope.
- Git history strategy for the extractions (filter-repo preserving tag ledgers vs. fresh starts); `capture-tool-v*` ledger continuity.
- Unity lock-file policy; whether `--embed`/`harvest` ships.
- uv auto-sync eviction prototype outcome (venv overlay vs. ephemeral patch).
- Dispositions: `rathole-client`, `apps/AndroidMobile`, UnityNuGet deprecation timing, the licensing pass (Stereolabs base image, vendored OkHttp) for the standalone repos.
- Renovate-class bump automation; `status` overlay column shape; sandbox/pgit template entries for the new repos.
