# Publishing redesign: in-house UPM derivation, three feeds, standing dev channel

## Scope

The publishing thread of the polyrepo initiative ([index](polyrepo.md)): own the UPM derivation, dual-feed publish (nuget + npm), a third feed on PyPI for the Python packages, and a public standing dev channel. Siblings: [prepo, the polyrepo workbench](polyrepo-workbench.md) and [repo boundaries](repo-extraction.md). This file keeps its original path (`package-publishing-redesign.md`) so pre-split ticket blob-links survive.

## Problem

1. A **public, standing dev channel**: every green `dev` push produces complete, installable, **immutable** bleeding-edge packages for every repo; `main` continues to produce stable releases through the release flow.
2. The generated C# clients stay **one authored package per client**, consumable by both Unity applications and non-Unity .NET applications.

UnityNuGet blocks requirement 1 structurally, and the current pipeline carries several latent defects discovered during forensics (below).

## Ground truth (verified 2026-09-18)

### UnityNuGet mechanics

- Ingestion is **stable-only**, and this is in the *code*, not just public-service policy: prerelease support was requested and declined upstream (xoofx/UnityNuGet#104) citing storage pollution and NuGet→npm/UPM semver remap mess. No prerelease version can ever flow through the public mirror, and a self-hosted stock instance inherits the same filter.
- Scan cadence: the registry re-scans nuget.org every **10 minutes** (`UpdateInterval`); OpenUPM's uplink syncs **hourly**.
- The curated list (`registry.json`) requires every transitive dependency to be explicitly listed, and new curated entries only appear after the maintainers' next Docker image release.

### Why UnityNuGet was adopted (T71, 2026-03-04)

The T71 plan and ticket record the decision: publish `vps`/`-arfoundation`/`-magicleap` to npmjs, route clients through UnityNuGet because they were "already published to NuGet and available via the UnityNuGet registry" — i.e. avoid duplicate publishing and get dependency derivation for free. The free-derivation premise had a concrete basis: the generated source packages carried **no `dependencies` block** (they still don't), while the UnityNuGet DLL repack derived the graph (`newtonsoft.json`, `polly`, `jsonsubtypes`) from the nuspec. The stable-only premise was harmless in a stable-only world; the dev-channel requirement breaks it.

### Present defects in the pipeline

- **api-client publish landmine**: `openapi-clientgen`'s `unity.py` strips the generated `.csproj` (to keep IDE `bin/`/`obj/` out of the UPM package); the last `Run generate-clients` (7ccbd750, 2026-06-05) deleted `PlaceframeApiClient.csproj`, but `publish_packages.py` still runs `dotnet pack` in that directory. The next stable release fails. `dev` already carries generate-clients changes since `placeframe-api-client-v0.1.7`, so the very next release hits it. **This is urgent independent of thread ordering** — the next stable release fails until it is fixed.
- **Zed client lineage fork** (c4dc285e, 2026-04-28, "Containerize ZED capture"): the `zed` project entry became `docker/zed-capture`; generated identity changed `PlaceframeZedClient` → `PlaceframeZedCaptureClient`, output dir `zed-client/` → `zed-capture-client/`; apps were repointed in the same commit. The cleanup never happened:
  - `packages/generated/csharp/zed-client/` is frozen (last touched 2026-05-03, regenerated by nothing — absent from `build/openapi-projects.json`) yet still wired into `publish_packages.py`/`create_release.py`.
  - It was even published once post-mortem: `placeframe-zed-client-v0.1.5` (2026-05-13), triggered by a design-notes doc move inside the dead tree tripping the path-diff change detection.
  - nuget.org serves `PlaceframeZedClient` 0.1.0–0.1.5 (an April-era API surface) and the UnityNuGet mirror serves it too, while the live successor `PlaceframeZedCaptureClient` — regenerated on every `generate-clients`, consumed by CaptureTool via `file:` — is published nowhere.
- **`org.outernet.placeframe.auth`** is a real UPM package (consumed by CaptureTool via `file:`) missing from the publish set entirely.
- **`org.outernet.logging`** likewise: consumed by CaptureTool via `file:`, version `0.0.0-local`, in no publish set anywhere.
- `com.placeframe.vps@1.0.0` is an orphaned pre-rename relic still live on npm (published 2026-03-05, nine minutes before the scope was renamed to `org.outernet.placeframe`).

### npm dist-tag behavior

- npm: dist-tags are floating pointers by construction; Unity's resolver has no dist-tag concept and its version ranges never jump a stable pin onto a prerelease (exact prerelease pins do resolve).

## Design

### Derivation moves in-house

```
openapi-clientgen (placeframe)              openapi-clientgen (zed repo)
  └─ emits UPM source package + csproj        └─ emits UPM source package + csproj
        │                                           │
  publication machinery repo (shared)        publication machinery repo (shared)
        ├─ dotnet pack ──► nuget.org                 ├─ dotnet pack ──► nuget.org
        └─ npm publish ──► registry.npmjs.org        └─ npm publish ──► registry.npmjs.org

Unity projects: scoped registry npmjs (org.outernet.*) + scoped registry UnityNuGet (third-party org.nuget.*)
```

The nuget package remains the general-purpose C# artifact. The UPM tarball is a **derived build output of the same generated tree** — never independently authored, never separately versioned. "Publish once" is preserved; what changes is that the Unity variant is derived by our pipeline instead of a third-party service that cannot carry prereleases.

### Identity

- npm: `org.outernet.placeframe.apiclient`, `org.outernet.placeframe.zedcaptureclient` (matches the existing `org.outernet.placeframe` / `-.arfoundation` / `-.magicleap` scope).
- Assembly names (`PlaceframeApiClient`, `PlaceframeZedCaptureClient`) are unchanged, so consumer `.asmdef` references survive the rename untouched. The new identities (`org.outernet.placeframe.apiclient`, `-.zedcaptureclient`, `placeframe-common`/`placeframe-core` on PyPI) are verified available.
- The Python `placeframe-core` distribution's config/tag name is `placeframe-core-python`: the Unity core package already owns the `placeframe-core-v*` tag space, and one tag prefix cannot serve two ledgers. `placeframe-common` has no such collision and uses its own name.
- The Python import names rename with the distributions (`placeframe_common`/`placeframe_core`). Keeping `common`/`core` would have put two generic top-level module names on a public registry (collision-prone in any consumer venv) and required a `[tool.deptry.package_module_name_map]` block in every consumer, present and future — the zed repo and capture-tool repo would inherit the config wart. Import-name == distribution name is the repo's existing convention (`placeframe_api_client`, `placeframe_localizer_client`).
- The UnityNuGet scoped registry stays in consumer manifests **for third-party packages only** (`org.nuget.polly`, `org.nuget.r3`, `org.nuget.mathnet.numerics`, …).

### Source package, not DLL repack

The published UPM artifact is the generated **source** package (asmdef), identical in shape to what in-repo projects consume via `file:` refs today. Rationale:

- Artifact unification: in-repo (`file:`) and external (registry) consumers get the same thing — one consumption contract, no drift.
- Zero conversion machinery: no nupkg→UPM repack step to own or fork (that machinery is what this design deletes).
- Consumers can read and debug the source.

Accepted tradeoff: the consumer's Unity compiler compiles the client, so the generated code's language level sets an implicit Unity floor. Guard: keep the patched generator templates at C# 8/9 (`csc.rsp` already enables nullable annotations, implying a C# 8 floor). We control both the templates and the Unity versions in use, so the exposure is bounded.

### Emitted dependencies

`package.json` gains a `dependencies` block — closing the one concrete gap that made UnityNuGet feel cleaner in T71:

- `com.unity.nuget.newtonsoft-json` — the Unity-blessed Newtonsoft. A 1:1 nuspec mapping (`org.nuget.newtonsoft.json`, what the UnityNuGet repack declares) collides with the Unity-provided assembly most projects already carry.
- `org.nuget.polly`, `org.nuget.jsonsubtypes` — third-party, resolved via the UnityNuGet scoped registry.
- Version **ranges**, not exact pins, so consumer manifests already carrying newer minors don't conflict.

### Versioning

- Committed `package.json` versions are permanently `0.0.0-local`; the real version is patched in ephemerally at publish time and never committed (same invariant as the existing Unity packages). Python `pyproject.toml` versions follow the same invariant with the PEP 440-valid sentinel `0.0.0.dev0` (`0.0.0-local` is not valid PEP 440 and would break every workspace build).
- Per-package git tags (`{package}-v{semver}`) remain the single version ledger; both feeds publish the **same semver** for the same release.
- `zed-capture-client` starts a fresh ledger at 0.1.0 in the zed repo (its predecessor's `placeframe-zed-client-v*` tags stay as historical record in placeframe). Its first publish — and the `PlaceframeZedClient` deprecation pointing at the successor — waits until the zed repo exists at the boundaries cutover; nothing in this thread depends on it.

### Python feed (PyPI)

The zed repo consumes placeframe's Python `common`/`core` packages (zed-capture imports them today); after extraction that consumption is cross-repo and needs an at-rest pin target. PyPI becomes the third feed: `placeframe-common` and `placeframe-core` publish on the same stable flow and dev channel as every other package. Rationale: the dev channel requires immutable `-dev.<run-id>` versions reachable by exact pin, which git-source pins cannot offer; PyPI has none of npm's dist-tag friction; registry pins keep `[project.dependencies]` declarative. This also fixes the uv link rewrite as a source-type swap (registry pin → `tool.uv.sources` path), symmetric with Unity's manifest rewrite.

### Publication machinery

The machinery repo is **`pubpkg`** — a new standalone repo (sibling of `unity-buildkit` / `stack-lifecycle` / `bashrun` / `openapi-clientgen`), the name verified unclaimed on GitHub/PyPI/npm. It owns: the publish pipeline, the per-package tag ledger and path-diff change detection, ephemeral version patching, `mirror-images` and the digest-pinned mirror scan, and release orchestration. placeframe, the zed repo, and the capture-tool repo all consume it from their own CI. Per-repo copies of this machinery are refused — it is written once; per-ecosystem splits are refused too (Discarded alternatives) — the seam is internal: one `Feed` adapter per registry (nuget, npm/UPM, PyPI, plus the OCI mirror scan) over the shared ledger/diff/versioning core.

Migration is absorptive, never duplicative: the publish/release cohort of `build/src/build_scripts/placeframe/ci/` — `publish_packages.py`, `create_release.py`, `ensure_release_pr.py`, `fetch_ci_artifacts.py`, `git_tags.py`, and the `mirror-images` command — is deleted from placeframe and lives only in pubpkg, invariants included (the CI-commit-free rules — tag ledger, path-diff detection, ephemeral `0.0.0-local` patching — migrate into pubpkg's `AGENTS.md`). placeframe keeps declarative package configuration only (package identities, tag prefixes, registry mappings) plus workflow files whose steps are thin invocations of pubpkg entry points, consumed the same way placeframe consumes `stack-lifecycle` and `unity-buildkit`: a git-referenced dependency providing `uv run` commands.

**Release units.** The repo is the release unit. Repos release independently; one release event publishes every changed package in the repo together; a package unchanged since its last tag is skipped — registries are immutable so there is nothing to publish, and emitted ranges absorb sibling bumps without republishing dependents. Per-package version numbers stay independent within the event (no lockstep numbering). Release-PR mechanics migrate from the existing flow rather than being redesigned: the standing `dev` → `main` "Next release" gate PR (`ensure_release_pr.py`), publishing on `main` push with path-diff detection and automatic patch-bump versions from the tag ledger (`publish_packages.py`, `git_tags.py`), CI-artifact reuse and the GitHub Release (`create_release.py`, `.github/workflows/placeframe-release.yml`) — all currently under `build/src/build_scripts/placeframe/ci/`.

**Feed auth** uses the strongest mechanism each registry supports — PyPI trusted publishing (OIDC) from each repo's workflow, npm trusted publishing (OIDC via `--provenance`; what the pipeline already uses, the token path having been retired), nuget.org API keys scoped to the package IDs — alongside the existing GitHub-App-token pattern for checkout and tag-push in `placeframe-release.yml`. PyPI trusted publishing needs no workflow secret (`uv publish` exchanges the OIDC token; the workflow already carries `id-token: write`), but each PyPI project needs a pending publisher configured for the consuming repo + workflow file before its first publish. npm allows exactly **one** trusted publisher per package, bound to a single workflow filename — so every npm publish path for a package (stable and dev) must ride the same workflow file. npm has no pending publishers: a brand-new npm identity needs a one-time bootstrap publish (token or manual) before its trusted publisher can be configured.

### Dev channel

- `main` → stable, via the existing release flow (release PRs + tags; the tag space is the stable version ledger).
- `dev` → every green push publishes **immutable** `-dev.<run-id>` prereleases of every changed package (path-diff detection as today) to that package's feeds (nuget + npm for the C# clients and UPM packages, PyPI for the Python packages). The run id is the identity; the version spelling is normalized per feed (`-dev.<run-id>` where semver allows it, `X.Y.Z.dev<run-id>` on PyPI — no single string is both valid semver and valid PEP 440).
- npm requires a non-`latest` dist-tag to publish a prerelease without moving `latest`; a single inert `dev` dist-tag exists as that plumbing only. **The version list is the interface**: consumers pin exact immutable versions. There is no discovery tooling by decision — no `prepo bump` resurrection, no registry-query verb, no bump bot; the dev-channel job prints the exact version it published and consumers pin it by hand. Floating-tag consumption (`pkg@dev`) is rejected.
- Unity consumes dev builds as exact version pins; its resolver never auto-jumps a stable range onto a prerelease.
- Dev publishes **never create git tags**.
- No standing services: all registries are public CDNs; publishing is a CI job.

## Discarded alternatives

- **Self-host a public UnityNuGet**: buys the same one-authored-package property but requires a permanent public HTTPS service *plus* a maintained fork (prerelease support doesn't exist in stock code) — renting the problem instead of solving it.
- **`UnityNuGet.Tool` in CI as the converter**: inherits the same stable-only filter, so it needs patching anyway, and it outputs the DLL-repack artifact shape.
- **Stable-formatted burn versions (99.x) through the public mirror**: a dev build would become "latest" for every consumer of the package page and Unity's Package Manager — exactly the pollution upstream declined prereleases to avoid.
- **Consume the nuget package in Unity via NuGetForUnity**: most literally one package/one feed, but it drops the client out of the UPM dependency graph (core can't declare it) and restores a duplicate-Newtonsoft conflict with `com.unity.nuget.newtonsoft-json`.
- **DLL repack as the published artifact**: keeps the conversion machinery this design deletes and forks the consumption contract into two artifact shapes (in-repo source vs external DLL).
- **Three per-ecosystem machinery repos** (PyPI / NuGet / npm publishers): the tag ledger is per-package, not per-feed — api-client's same-semver dual-publish spans the nuget and npm adapters, so a split either duplicates the ledger per feed or forces a fourth shared-core repo with cross-repo version skew; no consumer's surface shrinks (placeframe touches all three feeds regardless); and "Unity publishing" is not a real axis — the Unity-specific derivation lives in openapi-clientgen. Dominated by one repo with a hard internal `Feed` adapter seam.
- **Dev-channel discovery tooling** (`prepo bump` resurrection, a registry-query verb in the machinery repo, a Renovate-class bump bot): exact-pin-by-hand suffices — CI prints the published version — while any tooling re-adds a network surface or consumer-side producer tooling for a one-or-two-consumer workflow.
