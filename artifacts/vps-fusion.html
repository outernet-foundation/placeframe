Placeframe · VPS localizer and RelocalizationFilter

How VPS and VIO are fused

The headset tracks itself smoothly with VIO, but VIO's world has an arbitrary origin and drifts. VPS answers "where is this camera in the map?" now and then, with noise. The fusion filter keeps one estimate of how the VIO world sits inside the map, and nudges it with each VPS fix it trusts.

Parts 1 and 2 describe the general process and its parameters, with the values currently set in code and calibration. Part 3 analyses one recorded localization run. Part 4 recommends changes.

Part 1 · The process
Vocabulary

Three coordinate frames and one alignment

Unity world, UWhere VIO puts the camera: unity_from_camera, the device tracker's pose converted to Unity axes, plus the camera's mounting offset. Smooth and fast, but its origin is wherever tracking started, and it drifts as the user walks.
Map, MThe reconstruction's frame. VPS reports the camera's pose in it: camera_from_map.
ECEF, EThe geo frame content is authored in, related to the map by ecef_from_map.
unity_from_ecefThe "alignment": the one rigid transform the filter estimates. A point x in the map frame renders in Unity world at unity_from_ecef · ecef_from_map · x.

x is a 3-D point in the map frame, such as a map point or content anchored to the map, written as the homogeneous 4-vector [x, y, z, 1]. Transforms are 4×4 matrices written a_from_b: they take coordinates in frame b to frame a. They chain right to left, and matching inner frames cancel: a_from_b · b_from_c = a_from_c, and inv(a_from_b) = b_from_a. The frames are U (Unity world), M (map), E (ECEF) and C (camera). The code spells a_from_b as a_from_b. Elsewhere on this page "alignment" always means unity_from_ecef.

Every fix and every VIO pose of the same still together imply one unity_from_ecef. If VPS and VIO were perfect, every fix would imply the same unity_from_ecef. The filter's job is to average the ones that disagree only by noise, and ignore the ones that are wrong.

What the filter estimates

The one unknown is the alignment X = unity_from_ecef. It is the transform that makes VPS's camera pose, carried into Unity, land on VIO's camera pose:

unity_from_ecef ·ecef_from_map · map_from_cameraVPS camera pose in ECEF=unity_from_cameraVIO camera pose
  • Camera pose (unity_from_camera): an input from VIO. It changes every frame as the user moves.
  • Measurement Z, with covariance R: one fix's value of X, solved from that equation for a single still (stage 5). It carries that fix's full noise.
  • Estimate X̂, with covariance P: the filter's fused estimate of X from every accepted measurement, known in code as the filter's mean. Stage 7 compares each new Z with it, and stage 8 moves it partway toward Z.

The notation is standard Kalman-filter notation. A hat marks the filter's estimate. A superscript ⁻ means predicted, before a measurement is applied. Without it, X̂ and P are the filter's current state, which stage 8 overwrites with each accepted fix. ỹ is the innovation, and K the gain.

The alignment should stay nearly constant, changing only slowly as VIO drifts. So measurements taken seconds apart and from different places should agree. Their scatter is noise to be averaged out, unless a fix is simply wrong.

Pick a still to localize

The camera produces stills continuously. Every Δt_req = 1 s (the interval both the Capture Tool and Make it Sing pass to StartLocalizing), the device takes the latest one and sends it to the server. If a request is still in flight, that tick is skipped rather than queued. The answer arrives after a network and server latency L, by which time the user has moved on. The filter therefore pairs each answer with the VIO pose recorded when the still was taken, not the current one.

server · localizer

Retrieve, match, solve PnP

Find similar map images, then match the still's features to map points. Many matches are wrong, so RANSAC repeatedly solves a pose from a few random matches. Each time, it projects every matched map point and counts the inliers: matches that land within τ pixels of their feature. The pose with the most inliers is refined by pycolmap using only those inliers. The result is camera_from_map, the N inlier matches, and Σ_pnp: pycolmap's 6×6 uncertainty of the camera pose.

RANSAC_THRESHOLD_DEFAULT = τ = 8.0 px core/localization_metrics.py

The largest reprojection error a match can have and still count as an inlier. Raising it accepts more matches, including some wrong ones. Lowering it accepts fewer matches, and more stills end with no pose. A request can override it with ransac_threshold.

In angle, τ px is τ / f radians for focal length f px. At scene depth Z, a match can be off by about Z · τ / f sideways and still count as an inlier. For the ML2 still camera at the localizer's 1820 px width (f ≈ 1,430 px), 8 px is about 0.32°: 6 cm at 10 m, 17 cm at 30 m, 56 cm at 100 m. pycolmap's Σ_pnp assumes inliers are accurate to about 1 px, whatever τ is.

server · build_metrics, localize

Confidence gate

The server estimates how likely the pose is to be right, and refuses to return fixes that are probably wrong. It computes two confidences, each a probability between 0 and 1, with no units:

  • c_loose: the probability that the pose is within 30 cm and 5° of the truth.
  • c_tight: the probability that it is within 5 cm and 1°.

Each is a logistic regression over nine features of the fix, optionally followed by an isotonic remap that makes the output a calibrated probability. The features are log inliers, inlier ratio, normalised reprojection error, inlier coverage of the image, log matches, and four properties of the map: image count, point count, mean track length and viewpoint diversity.

c = isotonic( sigmoid( b + Σ wᵢ · featureᵢ ) ) reject if c_loose < c_loose,min or c_tight < c_tight,min

A rejected fix comes back as an error ("Confidence below gate: loose=…, tight=…"). The device gets no pose, so the filter never sees it. The dashboard's Details view still shows the pose and the two confidences.

The deployed calibration is a placeholder docker/localizer/calibration/global.json

Only the inlier weight is set (w = 1.2, b = −5.5, no isotonic step), and the tight model copies the loose one. Confidence is therefore just a function of the inlier count, c = sigmoid(1.2 · ln(1 + N) − 5.5). It is not a calibrated probability. The curve crosses c_loose,min = 0.25 at N ≈ 38.2, so a fix passes exactly when N ≥ 39 (38 inliers gives 0.249). Here N is RANSAC's inlier count from stage 2: matches within τ = 8 px of the RANSAC pose, counted before refinement. c_tight,min = 0, so the tight gate never rejects.

When the localizer loads this file, it warns that "Tight/loose confidence gates are no-ops". That is only true of the tight gate. The loose gate does reject fixes.

Measurement covariance

The uncertainty sent to the device with each fix is the PnP covariance scaled by α, plus β on every diagonal entry. The same β is added to rotation entries (rad²) and translation entries (m²), so it sets a floor of √β radians on rotation and √β metres on translation. The deployed α = 1 and β = 1e-3 give floors of 0.032 rad (1.8°) and 0.032 m (3.2 cm).

R = α · Σ_pnp + β · I₆
Σ_pnp: what pycolmap computes pycolmap 4.0.4 · estimate_and_refine_absolute_pose(return_covariance=True)

Inputs: the N RANSAC inliers i (matches within τ = 8 px), each a map point X_i (m, COLMAP map) and its keypoint u_i (px, upright 1820×1024 image); fixed pinhole intrinsics f_x, f_y, c_x, c_y; and the pose (R, t) = cam_from_world (pycolmap's cam_from_world), map → camera.

p_i = R X_i + t point in camera coordinates (OpenCV axes) π(p) = [ f_x p_x / p_z + c_x , f_y p_y / p_z + c_y ] r_i = π(R X_i + t) − u_i reprojection residual (px) s_i = ‖r_i‖² refine: (R̂, t̂) = argmin Σ_i ρ(s_i) ρ(s) = c² ln(1 + s/c²), c = 1 px (Cauchy) perturb: R ← Exp(2 δθ) · R half-angle, applied on the left t ← t + δt ξ = [δθ ; δt], order [rotation, translation] J_i = ∂r_i / ∂ξ at (R̂, t̂) 2×6 w_i = ρ′(s_i) = 1 / (1 + s_i / c²) Cauchy weight H = Σ_i w_i · J_iᵀ J_i 6×6 Gauss–Newton information Σ_pnp = H⁻¹ implicitly × σ², σ = 1 px

Reading the lines in order: r_i is each inlier's reprojection residual in pixels through the pinhole projection π; the pose is refined under a Cauchy loss ρ with scale c = 1 px; the pose is perturbed by ξ = [δθ; δt], rotation first; J_i is the residual's 2×6 Jacobian at the refined pose: two pixel rows, six pose columns. In it, Π_i is the projection's 2×3 Jacobian at p_i, and [q_i]× is the cross-product matrix of q_i, the map point rotated into camera axes but not translated. The rotation columns use q_i rather than p_i because δθ pivots about the map origin, and the factor 2 comes from the half-angle; w_i is the Cauchy weight; and Σ_pnp is the inverse of the weighted Gauss–Newton information, implicitly scaled by σ² with σ = 1 px.

δθ rotates the map about its own origin, in camera axes, by twice ‖δθ‖ (half-angle, applied on the left), so the rotation block's variance is ¼ of the rotation-vector variance the filter assumes. δt moves the map origin, also in camera axes. The units are half-angle rad² and m².

Each point is treated as an independent observation with 1 px noise, and the map points as exact. Residual size enters only through the weights w_i. These widen Σ_pnp roughly in proportion to each point's squared residual, but there is no other rescaling: with the loss switched off, 1 px and 3 px noise give the same covariance. Correlated errors between points, map-point error and wrong matches are not modelled.

These equations were checked against pycolmap on synthetic data. With the weights, they reproduce its covariance exactly (the eigenvalues of the ratio are 1.000 at 1 px and 3 px of noise).

Into the filter's tangent space

The gate needs R in the alignment's tangent space, the same space as ỹ. When ecef_from_map is identity, carrying Σ_pnp there is block-diagonal. The floor is meant in the filter's units already, so it is added afterwards:

R = α · A Σ_pnp Aᵀ + β · I₆, A = [ 2Q 0 ] [ 0 Q ]

Q is the fixed 3×3 rotation from the camera's axes to the filter's ECEF axes, with the axis flips folded in. No lever-arm term is needed: pycolmap's δθ is already a rotation about the map origin, the point the alignment's tangent also uses. So the coupling that comes from the camera sitting far from that origin is already inside Σ_pnp's off-diagonal blocks. This was checked numerically on a fix 24 m from the map origin: the off-diagonal block of A came out at 1.4e-8. Today the server and stage 5 use A = I, so Σ_pnp stays in camera axes with rotation in half-angle units.

fit-calibration scripts/src/scripts/fit_calibration.py · uv run fit-calibration

The offline tool meant to produce global.json from ground truth. It:

  • takes capture sessions with known camera poses (frames.csv), holds some frames out, and builds a reconstruction from the rest;
  • localizes each held-out frame through the API at default settings, and stores its metrics, Σ_pnp and its error against the known pose (err_t_m, err_r_deg, and the 6-D se3_residual);
  • fits the stage 3 confidence models. These are logistic plus isotonic, labelled by whether the error is under 30 cm and 5° (loose) or 5 cm and 1° (tight);
  • fits α and β by maximising the Gaussian likelihood of the residuals under α·Σ_pnp + β·I;
  • writes global.json.

The deployed file was never produced this way: it records sample_count 0 and pipeline_version "placeholder". Even once fitted, the model has one β shared between rad² and m².

Is R measured or fixed?

It is computed for each fix, but the floor usually dominates. A rotation floor of 1.8° is far larger than PnP's rotation σ for any well-constrained fix, so the rotation part of R is effectively constant. The translation part rises above 3.2 cm only when PnP's own translation σ is comparable to it: few inliers, far points, or points bunched in one part of the image.

device · filter

Predict: let uncertainty grow

Before comparing, the filter widens the covariance P of its estimate X̂ to allow for VIO drift since the last accepted fix. The estimate itself does not move: X̂⁻ = X̂. P is whatever the previous cycle left: the result of the last stage 8 update, the widened P⁻ from a rejection, or P₀ before any fix. d is the straight-line VIO displacement since the last accepted fix, not the path length, so walking in a loop or turning in place adds nothing. After a rejection the full (k_drift · d)² is added again at the next fix, so the drift term grows faster than d². Before any fix, P starts at the bootstrap values, which are wide enough that the first fix always passes.

X̂⁻ = X̂ (the estimate itself does not move) P⁻ = P + diag(q_r ×3, q_t ×3) + (k_drift · d)² · I₆ X̂₀ = I₄ P₀ = diag(σ_r0² ×3, σ_t0² ×3) q_r = 1e-6 rad² q_t = 1e-4 m² k_drift = 0.01 per m σ_r0 = π rad σ_t0 = 100 m

Because k_drift is added to all six axes, it allows 1 cm of translation and 0.01 rad (0.57°) of rotation per metre walked.

device · filter

Innovation gate

Compute the innovation ỹ: the difference between the predicted estimate X̂⁻ and the measurement Z, as a 6-vector in the alignment's tangent space. Weigh it by the combined uncertainty to get m², the squared Mahalanobis distance (MahalanobisSquared in code). Reject the fix if it is too unlikely.

ỹ = log( (X̂⁻)⁻¹ · Z ) [rotation, translation] m² = ỹᵀ (P⁻ + R)⁻¹ ỹ reject if m² > χ²_gate

If P⁻ and R are honest, m² follows a χ² distribution with 6 degrees of freedom, and χ²_gate = 16.81 is its 99th percentile. When a fix is rejected, X̂ stays as it was, and the widened P⁻, capped at the bootstrap value, becomes the new P. The gate is then wider for the next fix. It widens quickly only while the user walks; the figure under stage 8 shows the cycle.

The first fix

The first fix goes through this same gate; it is not exempt. P₀ is set very high (σ_r0 = π rad, σ_t0 = 100 m) so that the gate passes it. With P⁻ ≈ P₀, m² ≈ |θ|²/π² + |t|²/(100 m)², where θ and t are the rotation and translation of Z. The rotation term is at most 1, so the fix passes whenever |t| ≲ 400 m. That holds when the filter's ECEF is the map frame (map_transform = identity), since Z's translation is then only the distance between the Unity and map origins. For a map placed at real ECEF coordinates (|t| ≈ 6,400 km) the first fix would be rejected. Because P is capped at P₀, no later fix could pass either.

Once the first fix passes, K ≈ 1 on every axis, so X̂ ≈ Z and P ≈ R, and the published alignment snaps to it.

Kalman update

An accepted fix moves the estimate part of the way toward the measurement, weighted by the gain K. The gain is large when the filter is unsure and small when it is confident.

K = P⁻ (P⁻ + R)⁻¹ X̂ ← X̂⁻ · exp(K ỹ) P ← (I − K) P⁻ (Note: P⁻¹ ← (P⁻)⁻¹ + R⁻¹)
How much an accepted fix shrinks P

The update is always P ← (I − K)P⁻. Substituting K gives P = P⁻(P⁻ + R)⁻¹R, which is the note's form: the information from the prediction and from the fix add. Per axis, P = P⁻R / (P⁻ + R), so the new P is always smaller than both P⁻ and R. How much smaller depends on their ratio:

  • P⁻ ≫ R (the first fix, or after many rejections): K ≈ I, the estimate jumps to the fix, and P ≈ R.
  • P⁻ ≈ R (typical between accepted fixes): K ≈ ½I, the estimate moves halfway, and P ≈ R/2.
  • P⁻ ≪ R (a fix much less certain than the estimate): K ≈ 0, and the fix barely changes X̂ or P.

The middle case is the usual one once the filter is running. After an accept, the prediction adds only the process noise before the next fix: 1 cm² plus (1 cm per metre walked)². For a user standing still with R = (3.2 cm)², P⁻ ≈ 10.2 + 1 ≈ 11 cm², and the update gives P ≈ 11 · 10.2 / 21 ≈ 5.4 cm², about half of R. Over successive accepts with little walking, P keeps shrinking roughly like R/n until it balances the process noise. So the filter tightens with every accepted fix, and the next fix must agree more closely to pass the gate.

"Bypass Kalman update" (below) sets P ← R instead, whatever P⁻ was. That is always the first case's result, so it never tightens the way the real update does.

Part 3 · Analysis of one run
Run cd35267b · map 261022_fosun_zed · ML2

The covariance is wrong in both directions

The short version. With the placeholder β, each fix tells the filter its position is good to about ±3 cm. In this run, fix positions actually scatter by about ±16 cm, with p90 near ±50 cm. Rotation is the opposite: fixes claim ±1.8° but agree to about ±0.2°. The filter trusts position 5× too much, so two out of three fixes look impossible to it and get thrown away.

How this run looks at each stage:

  • Stage 1: Δt_req = 1 s, and answers took L ≈ 2 s. Stills arrived at 4 Hz, so 249 stills were recorded and the device's schedule would have sent 33.
  • Stage 2: τ = 8 px with f ≈ 1,430 px is about 0.3°. Matched features sit 20–100 m away, typically 60–80 m, so an inlier can be 35–40 cm off sideways. The median inlier error was 2.8 px.
  • Stage 2: PnP failed outright on only 1 of 249 stills. It returned "poses" from as few as 3 inliers.
  • Stage 3: 26 of 249 stills fell below c_loose,min. Their inlier counts split in two: 18 had 3–11 inliers, almost certainly chance alignments, and 8 had 26–36, which were borderline. Accepted fixes had at least 41 inliers, with a median of about 1,800. The gate catches the junk tail, but above 39 inliers it accepts everything, so it says nothing about the quality of a typical fix.
  • Stage 4: PnP's own σ is tiny: 1.0 cm median for translation, and 0.006° for rotation in pycolmap's half-angle units (0.012° as an angle). PnP supplies 0.001% of R's rotation variance (at most 0.17%), so rotation in R is constant. For translation it supplies 10% at the median and 63% at p90. 65% of fixes report within 10% of the 3.2 cm floor, with p90 5.2 cm and a maximum of 18 cm.
  • Stage 7: 27 of 33 scheduled fixes were rejected.

The filter has no ground truth to check fixes against, but it does have neighbours: fixes from consecutive stills, 0.25–0.5 s apart. Neighbours see nearly the same scene, so they should imply nearly the same alignment, and their disagreement measures VPS noise directly. The chart converts it to a per-fix, per-axis σ and puts it next to what each fix reports. Data: 216 consecutive pairs out of 222 successful offline fixes.

Why this R rejects good fixes

Start from stage 7's gate:

m² = ỹᵀ (P⁻ + R)⁻¹ ỹ reject if m² > χ²_gate = 16.81

The rotation terms contribute almost nothing (median 0.02), so only the three translation axes matter. Treating each as independent:

m² ≈ Σ over 3 axes of ỹ² / (P⁻ + R)

With today's R. Per axis, typical values for this run:

m² ≈ 3 × (23 cm)² / ( (3.8 cm)² + (3.2 cm)² ) = 3 × 529 / (14.4 + 10.2) ≈ 65 > 16.81 → reject
  • ỹ ≈ 23 cm: the last accepted fix had K ≈ 1, so X̂ is essentially that fix. ỹ is then the gap between two fixes. Each fix scatters by about 16 cm per axis (see the chart above), so the gap between two is about 16 × √2 ≈ 23 cm.
  • P⁻ ≈ (3.8 cm)²: after that accept, P fell to just under R, about (3.05 cm)². Stage 6 then adds q_t = (1 cm)² plus (k_drift · d)² = (2 cm)² for about 2 m of walking before the next fix.
  • R ≈ (3.2 cm)²: the β floor, √(1e-3) m. PnP's own share is small for most fixes.
  • m² ≈ 65: about four times the threshold. The fix is rejected although nothing is wrong with it. The gate's yardstick, √(P⁻ + R) ≈ 4.9 cm, is a fifth of the real gap between fixes. P has to climb to about (9 cm)² before a typical fix passes; see the figure under stage 8.

With the proposed R = (20 cm)². Fixes are now accepted routinely, so X̂ and P settle at different values too:

m² ≈ 3 × (17.4 cm)² / ( (6.9 cm)² + (20 cm)² ) = 3 × 303 / (47 + 400) ≈ 2.0 < 16.81 → accept
  • ỹ ≈ 17 cm: K is now well below 1, so X̂ is an average of recent fixes rather than a copy of the last one. ỹ is the new fix's own scatter (16 cm, as observed) combined with X̂'s smaller error (about 6.9 cm): √(16² + 6.9²) ≈ 17.4 cm.
  • P⁻ ≈ (6.9 cm)²: the steady state when every fix is accepted. Each update shrinks P (P⁻¹ ← (P⁻)⁻¹ + R⁻¹), and each prediction adds back q_t + (k_drift · 2 m)² ≈ (2.2 cm)². The two balance at about 6.9 cm.
  • R = (20 cm)²: the proposed translation floor, slightly above the fixes' observed per-axis scatter of 16 cm, to leave some margin.
  • m² ≈ 2.0: a perfectly matched R would give about 3 over three axes on average. The proposed R is slightly conservative, so m² comes out a little lower. A typical fix passes with plenty of margin, and only real outliers reach 16.81.
Why

Where the bad covariance comes from

The calibration is a placeholder

The note in global.json says it is hand-tuned and that no fit-calibration corpus exists yet. α = 1 keeps pycolmap's covariance as is. β = 1e-3 was picked so the gate would roughly match "14 cm or 7.4°". That cutoff is reasonable for one axis at a time. But m² sums all six axes, and neighbouring fixes in this run are typically 35 cm apart.

One floor for two units

β·I adds the same number to rad² and m². 1e-3 rad² is generous for rotation (1.8°) and stingy for translation (3.2 cm). Because rotation needs a smaller floor and translation a larger one, no single β can be right for both.

PnP's covariance is small, but it ranks fixes well

pycolmap assumes 1 px pixel noise, with no map-point error and no wrong matches, while τ admits inliers up to 8 px off. Its translation σ is 1 cm here, an underestimate of about √150 ≈ 12×. Its rotation block is also in half-angle units, so the filter reads PnP's rotation σ as half the real angle. Its shape still carries information: its translation σ ranks the fixes' real disagreement with Spearman 0.71. The inlier count, which drives the stage 3 confidence, manages only −0.22. Scaled up properly, Σ_pnp is worth keeping.

The scene is far away

At 60–80 m, turning the camera 0.3° looks almost the same as moving it 35 cm sideways. PnP then pins rotation well and position poorly, with the two strongly coupled. The β floor throws that coupling away.

The covariance is in the wrong frame

Σ_pnp is expressed in the camera's axes, with rotation in half-angle units. The gate compares it with innovations in the alignment's tangent space, in ECEF axes. Stage 5 passes R through unchanged. The conversion it skips is only an axis rotation Q and a factor of 2 on rotation (stage 4). No lever-arm term is missing: pycolmap already measures rotation about the map origin, so the coupling from the camera sitting 24 m from it is already in Σ_pnp. That coupling is real; the observed alignment noise has a rotation–translation correlation of 0.64. Today the floor hides all of this, because β·I looks the same in any axes. Once α scales Σ_pnp up, its long axis, typically depth along the camera's view, would be applied along the wrong ECEF direction.

Secondary: process noise mixes units, and recovery depends on walking

k_drift goes on all six axes, so rotation grows 0.57° per metre walked, far more than the ML2's real VIO drift. After rejections, P opens up quickly only while the user walks, so someone standing still keeps being rejected. For a fix 23 cm off per axis to pass, P⁻ must grow from about (3.05 cm)² to about (9.2 cm)². Standing still, only q_t = 1e-4 m² is added per evaluated fix, so that takes about 76 fixes. At one fix every 2 s, that is about 150 s, or 2½ minutes. Walking about 2 m between fixes, the drift term gets there in about 4 fixes, or 8 s.

Separate issue: map scale

Map distances come out 1.16× the tracked distances in this run (1.13 on 1b7ec841). An SE(3) filter can't represent scale, so content drifts in proportion to distance from the last accepted fix. This is independent of the covariance problem. The window algorithm's Sim(3) option in fusion-test was built to probe it.

Part 4 · Recommendations
What to change

Recommended changes, in order

now

Separate rotation and translation floors

Replace β·I with diag(β_r ×3, β_t ×3). Start from 0.3° and 20 cm, the values that gave the gain shown in part 3. This one-line calibration change can live on the server (global.json gains two fields) or as a device-side override while testing.

fusion-test: add a covariance_model option to KalmanParams (raw | diag | scaled_pnp | propagated) and sweep it.

next

Put the covariance in the frame the filter uses

Carry Σ_pnp into the alignment's tangent space before adding the floor, R = α · A Σ_pnp Aᵀ + β · I, where A = blockdiag(2Q, Q) (stage 4). Q rotates camera axes into the filter's ECEF axes, and the 2 converts pycolmap's half-angle rotation. No lever-arm Jacobian is needed, because Σ_pnp already measures rotation about the map origin. A non-identity ecef_from_map would add its own rotation to Q, plus a lever-arm term from the map origin's offset in ECEF. A depends only on the fix's own pose, so the server can apply it. This matters once α lifts Σ_pnp above the floor; with the diagonal floor alone it changes nothing.

next

Fit the calibration on data

Run fit-calibration on a ground-truthed corpus to fit α, separate floors, and the stage 3 confidence models. The one run here suggests α ≈ 150. Consider a depth-aware term, σ_t ≈ Z × angular noise, since far scenes are where position falls apart. Until a ground-truth corpus exists, neighbour consistency (the method in part 3) can stand in as the likelihood. Also correct the localizer's "gates are no-ops" warning, since the loose gate is live.

later

Make rejection softer and recovery time-based

Gate rotation and camera position separately, so one bad axis doesn't hide the other. Downweight large residuals (Huber or Student-t) instead of a hard cut. Grow uncertainty with time as well as distance, and re-bootstrap after a run of consecutive rejections, so a user standing still can recover.

later

Fix process-noise units, and address scale

Split k_drift into separate rotation (closer to 0.05°/m) and translation (1 cm/m) terms. Then decide whether to correct map 1b7ec841's scale or let the filter estimate scale (Sim(3)). The window algorithm's fit_scale in fusion-test is the place to try the second option first.
