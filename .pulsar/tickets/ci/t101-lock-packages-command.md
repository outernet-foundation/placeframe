# T101: Consolidated lock-packages command with CI preflight check

## Goal

Replace the existing `generate-lock-files` script with a comprehensive `lock-packages` command that makes all lock files in the monorepo consistent — Python (uv workspace lock + per-service pylock exports) and Unity (packages-lock.json via batchmode) — with a `--check` flag for CI preflight validation.

## Context

### The problem

The monorepo has multiple types of lock files that can become stale independently:

1. **`uv.lock`** (workspace root) — resolves all Python deps including three PyTorch variants (CPU, CUDA, ROCm) via extras + conflicts + explicit indexes on `download.pytorch.org`.
2. **`docker/*/pylock.*.toml`** (per-service) — exported from the workspace lock via `uv export --frozen`. Services like localizer and reconstructor have variant-specific exports: `pylock.neural-networks-cpu.toml`, `pylock.neural-networks-cuda.toml`, `pylock.neural-networks-rocm.toml`.
3. **`*/Packages/packages-lock.json`** (per Unity project, 5 total) — generated by Unity's package resolver during project open/import.

Today, only step 2 has a script (`generate-lock-files`). Steps 1 and 3 are manual. There is no validation that any of these are up to date in CI.

### Why this matters now

A recent refactor (T71, scoped UPM registry) changed how Unity packages are referenced. All monorepo `manifest.json` files now use `org.nuget.placeframeapiclient` as the package name (matching the NuGet registry name) with `file:` overrides pointing to the local generated source. This ensures:

- **Monorepo development**: `file:` reference means local edits take effect immediately without a publish cycle.
- **External consumers**: The Core package's `package.json` declares `"org.nuget.placeframeapiclient": "0.1.5"` as a versioned dependency. External consumers (not in the monorepo) resolve this from the UnityNuGet scoped registry automatically — no `file:` override.
- **Transitive resolution works**: Unity DOES resolve transitive dependencies for local `file:` packages (unlike git URL dependencies, which do NOT resolve transitively). The scoped registry entries in `manifest.json` tell Unity where to find `org.nuget.*` packages. A direct `file:` reference in `manifest.json` overrides the registry version, using the same package name (`org.nuget.placeframeapiclient`), so Unity sees one package, not two.

The original error that triggered this investigation was: "Plugin 'Packages/org.nuget.placeframeapiclient/lib/netstandard2.1/PlaceframeApiClient.dll' has the same filename as Assembly Definition File 'Packages/com.placeframe.api-client/PlaceframeApiClient.asmdef'." This happened because two packages with different names (`com.placeframe.api-client` via `file:` and `org.nuget.placeframeapiclient` via transitive registry resolution) both produced an assembly called `PlaceframeApiClient`. The fix was to use a single package name (`org.nuget.placeframeapiclient`) everywhere, with `file:` overrides in monorepo manifests.

### PyTorch and uv lock performance

The neural-networks package (`packages/python/neural-networks/pyproject.toml`) uses three mutually exclusive extras (cpu, cuda, rocm) with `tool.uv.conflicts` to enforce single-variant installation. Each variant maps to a distinct PyTorch index (`download.pytorch.org/whl/{cpu,cu128,rocm6.4}`) via `tool.uv.sources` with `explicit = true`. The workspace `uv.lock` resolves all three variants.

Key performance facts:
- `uv lock --check` is instant — no network, no downloads, just validates the existing lock against pyproject.toml hashes.
- `uv export --frozen` is fast — reads from the existing lock, no resolution.
- `uv lock` (actual re-resolution) contacts PyTorch indexes but uses HTTP range requests for metadata (PEP 658 or zip central directory), so it does NOT download full 2-3GB wheels. Still slower than `--check` due to network round-trips.
- The per-service `generate-lock-files` export uses `--frozen`, so it's always fast.

### Unity lock validation

Unity has no equivalent of `uv lock --check`. The only way to authoritatively validate a `packages-lock.json` is to open the project in Unity batchmode and let the package resolver run. This is slow (minutes per project) but correct. There are 5 Unity projects in the monorepo:
- `legacy/Outernet.Client/`
- `apps/AndroidMobile/`
- `apps/MakeItSing/`
- `apps/MapRegistrationTool/`
- `packages/unity/Placeframe/`

### CI strategy

The CI distinction is by dispatch type, not branch:

- **Triggered builds** (push/PR to dev/main): Run `lock-packages --check` as a preflight step. If any lock file would change, fail before building anything. This is the gate that protects shared branches.
- **Manually dispatched builds** (workflow_dispatch on feature branches): Skip preflight entirely. Engineers iterating on feature branches don't need the friction. Stale locks don't break builds — Unity resolves on the fly, uv resolves on the fly — they just mean the committed lock doesn't reflect what was actually built.

The extra minutes from Unity batchmode only apply to the PR merge path, which is already a slower, deliberate process.

### Design decisions made

1. **Command name: `lock-packages`** (not `lock`). "lock" is ambiguous because `build_docker.py` also locks Docker image digests into `.env.lock`. "lock-packages" is unambiguous.
2. **`--check` flag does resolution + diff, writes nothing.** For Python: `uv lock --check` (instant) + `uv export --frozen` and diff against committed pylock files (fast). For Unity: batchmode per project + diff against committed `packages-lock.json` (slow but necessary). Exits non-zero with clear message if anything would change. This pushes validation logic into Python and out of GitHub Actions YAML.
3. **Scoping flags**: `--python-only` (skip Unity), `--unity-only` (skip Python), `--project <name>` (limit Unity to a specific project). Default is "lock everything."
4. **Replaces `generate-lock-files`.** The new command subsumes its functionality. The entry point in `scripts/pyproject.toml` changes from `generate-lock-files` to `lock-packages`. CLAUDE.md command table updated accordingly.
5. **No separate `--check` for Unity only.** Even in check mode, Unity must actually run. The `--check` flag just means "don't commit the result, just diff it." The cost is the same either way.

### Unity editor discovery

Unity batchmode needs to find the editor binary. Different environments have it in different places, and the monorepo may eventually use multiple Unity versions across projects.

Resolution order:
1. `unity-editor` on PATH (CI containers already have this)
2. Read version from `ProjectSettings/ProjectVersion.txt`, search platform-specific paths:
   - Linux: `/opt/unity/<version>/Editor/Unity`, `~/Unity/Hub/Editor/<version>/Editor/Unity`
   - Windows: `C:\Program Files\Unity\Hub\Editor\<version>\Editor\Unity.exe`

`xvfb-run` prefix is only added on Linux when available (needed for headless X11). Not needed/available on Windows.

### Unity tracked-file guard

Unity batchmode can silently modify tracked files beyond `packages-lock.json`. Observed behavior on the Placeframe project:
- Re-sorts `manifest.json` entries alphabetically
- Adds host-platform-specific toolchain packages (e.g. `com.unity.toolchain.linux-x86_64` on Linux, `com.unity.toolchain.win-x86_64-linux-x86_64` on Windows) — these are host-dependent, different per platform
- Reformats JSON arrays (inline → multi-line)

These modifications are unacceptable in CI. The guard works as follows:

After any Unity batchmode invocation (both `lock-packages` and `build-unity`), check `git diff --name-only` scoped to the project directory. Gitignored files are irrelevant. Three categories of tracked-file changes:

1. **Intended output** — `Packages/packages-lock.json` in `lock-packages` normal mode only. Hardcoded as a special case, not part of any whitelist. This is why the command exists.
2. **Whitelisted noise** — files Unity is known to modify that have been investigated and accepted as unavoidable. Starts empty. Shared across all call sites (`lock-packages` and `build-unity`). Silently restored via `git checkout`.
3. **Unexpected changes** — anything else. Report and fail.

In `lock-packages --check` mode, there is no intended output — any tracked-file change is a problem (stale locks or unexpected modifications). Everything gets restored.

### Gitignore BuildInfo.generated.cs

`build_unity.py` writes `BuildInfo.generated.cs` (embeds commit SHA) before invoking Unity. This is generated content that changes every build and should not be tracked. Gitignore it so the tracked-file guard doesn't flag it.

## Approach

Plan: `.pulsar/plans/t101-plan.md`

Build a new `lock-packages` script in the `build` project using typer (entry point `:app`) with three phases: (1) Python workspace lock via `uv lock`, (2) per-service pylock export via `uv export --frozen --format pylock.toml`, (3) Unity batchmode per project with editor auto-discovery and tracked-file guard. The `--check` flag runs all phases but uses `git diff` to detect changes instead of writing. Scoping flags (`--python-only`, `--unity-only`, `--project`) control which phases run. CI workflows add a preflight job that runs `uv run lock-packages --check` on triggered builds only (not `workflow_dispatch`).

A shared tracked-file guard utility (`build/src/build_scripts/check_tracked_files.py`) is used by both `lock-packages` and `build-unity` to detect unexpected modifications after Unity batchmode.
