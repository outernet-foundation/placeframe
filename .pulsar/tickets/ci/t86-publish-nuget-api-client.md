# T86: Content-hash versioning and automated publishing for UPM and NuGet packages

## Goal

Automate version bumping and publishing for all 4 packages in `publish-upm.yml`, with content-hash-triggered semver and version pinning back into consumer manifests. Currently versions are bumped manually — if someone changes package source but forgets to bump the version, CI silently skips publishing and the registry stays stale. This already bit us with the NuGet API client (`org.nuget.placeframeapiclient@0.1.3` missing `LocalizationMetrics` fields).

Packages in scope:
- `org.outernet.placeframe` (Core) — npmjs.org
- `org.outernet.placeframe.arfoundation` — npmjs.org
- `org.outernet.placeframe.magicleap` — npmjs.org
- `PlaceframeApiClient` (→ `org.nuget.placeframeapiclient` via UnityNuGet) — NuGet.org

Out of scope: `org.outernet.cesium-unity` — different lifecycle (manual `workflow_dispatch`, upstream version tracking, 30-60 min build). Can reuse the manifest-update mechanism later.

## Context

The 3 UPM packages are published by `publish-upm.yml` to npmjs.org. Each step checks `npm view` and skips if the version already exists — but the version must be bumped manually in each `package.json`. Same failure mode as NuGet: human forgets to bump → CI skips → stale.

The NuGet API client is generated from the OpenAPI spec via `uv run generate-clients`. Source lives at `packages/generated/csharp/api-client/src/PlaceframeApiClient/`. The publish pipeline is: `dotnet pack` → `.nupkg` → NuGet.org → UnityNuGet service auto-converts to npm → Unity consumers resolve from `unitynuget-registry.openupm.com`. NuGet.org currently has versions up to `0.1.4` (manual publishes). The `.csproj` is regenerated on every `generate-clients` run with version `0.1.0` (hardcoded in `scripts/openapi-generator/configs/csharp.json`), so the version must be overridden at pack time via `dotnet pack -p:Version=X.Y.Z`.

### NuGet pipeline details

- The `.csproj` targets `netstandard2.1` only
- `.csproj` is regenerated by openapi-generator — cannot add MinVer/Nerdbank.GitVersioning to it, cannot persist version in it
- `dotnet pack -p:Version=X.Y.Z` overrides the version at pack time without touching generated files
- UnityNuGet auto-picks up new versions from NuGet.org (~10 min polling) — no PR needed to their registry after initial whitelist
- Non-Unity .NET consumers can use the package directly from NuGet.org

### API client dual identity

The API client has two package names:
- `com.placeframe.api-client` — local dev (file reference in `packages/unity/Placeframe/Packages/manifest.json`)
- `org.nuget.placeframeapiclient` — published (auto-generated by UnityNuGet from NuGet package ID)

The placeframe Core package uses the API client (`using PlaceframeApiClient.Model;` etc.) and should declare `org.nuget.placeframeapiclient` as a dependency in its published `package.json` (see design decisions). The `file:` reference in the Placeframe workspace manifest should be replaced with the UnityNuGet registry reference.

### Monorepo consumer strategy

This section documents the analysis of how monorepo consumers (MapRegistrationTool, Outernet.Client) should reference internal packages, and the fundamental tension between local development and registry validation.

**The core tension.** Unity's package manager has no workspace protocol equivalent. Other ecosystems solve this cleanly:
- pnpm: `workspace:*` resolves locally, rewrites to version at publish time
- Cargo (Rust): `path = "../foo"` + `version = "1.0"` in same declaration — path used locally, version used when published
- Go: `replace` directives override resolution locally, ignored when consumed externally

Unity offers none of these. A dependency is either a `file:` reference (local, immediate iteration, no transitive resolution) or a version string (registry, transitive resolution works, must publish to see changes). No dual mode.

**`file:` references lose transitive resolution.** Unity's package manager does not resolve transitive dependencies for `file:`-referenced packages. Each consumer must explicitly list every dependency. With registry references, consumers get transitive resolution (e.g. adding MagicLeap automatically pulls ARFoundation and Core).

**Embedded packages.** Packages physically in a project's `Packages/` directory are treated as "embedded" and do get transitive resolution. Symlinks could theoretically achieve this for monorepo packages, but this is unvalidated at scale and introduces cross-platform problems (Windows symlinks, `.meta` file behavior).

**No Unity hooks before package resolution.** Package resolution is the very first thing Unity does on startup — before any C# code compiles. There is no pre-resolution hook. The only way to generate `manifest.json` before resolution would be wrapping the Unity launch command externally, which is fragile.

**The `.env.lock` / `.env.local.lock` layering pattern doesn't translate.** Docker Compose natively supports layered env files (`env_file: [.env.lock, .env.local.lock?]`). Unity's `manifest.json` has no override/layering mechanism — it's a single flat JSON file. You can't gitignore it because it contains scoped registry configuration and dozens of Unity module dependencies that must be tracked.

**Conclusion: monorepo consumers use `file:` references for local development.** This is the pragmatic choice — developers get immediate iteration without publishing. The trade-off is explicit dependency listing (no transitive resolution), which is acceptable for 3-4 internal packages.

**Testing gap.** If all monorepo consumers use `file:` references, nothing in the repo exercises the registry resolution path. A package could have a broken `package.json` (wrong dependency name, missing dependency) and no one would know until an external consumer hits it.

### Custom Unity editor resolver (explored, rejected)

Explored whether a custom `[InitializeOnLoad]` editor script (inspired by [mob-sakai/GitDependencyResolverForUnity](https://github.com/mob-sakai/GitDependencyResolverForUnity)) could add transitive dependency resolution for `file:`-referenced packages. The mob-sakai plugin works by scanning packages for a `gitDependencies` field, cloning missing deps, and installing them as embedded packages in `Packages/`. It lives in its own `.asmdef` so it compiles independently of broken deps.

A simpler version: an `[InitializeOnLoad]` script that scans `file:`-referenced packages' declared dependencies, finds unresolved ones, and adds them via `UnityEditor.PackageManager.Client.Add()`.

**This breaks down.** `Client.Add()` would resolve the missing dependency from the **registry** (an immutable published copy), not from local source. So you'd get ARFoundation pointing at local source (editable) but its transitive dependency Core frozen at the last-published registry version. Editing local Core source would have no effect — defeating the purpose of `file:` references.

To truly resolve locally, the script would need to detect that the package exists in the monorepo and add it as a `file:` reference or symlink it into `Packages/`. This is essentially reimplementing a workspace protocol from scratch — a significant engineering effort for a fragile result (custom tooling every developer must have, fights Unity's own resolver, cross-platform symlink issues).

**State file format (decided):** Uniform version + hash per package in `publish-state.json` at repo root. See Design decisions.

## Design decisions

- **Publish NuGet to NuGet.org, not npmjs.org directly**: NuGet.org is the standard .NET registry. Non-Unity .NET consumers can use the package directly. UnityNuGet auto-converts for Unity consumers.
- **All 4 packages in `publish-upm.yml`**: Keeps all Unity-related package publishing in one place. The workflow is thin and fast. (Previously T87 was a separate ticket for the UPM packages — folded in since it's the same problem.)
- **Content-hash-triggered semver**: Hash source to detect changes, auto-bump patch, publish only when content differs. Clean semver versions, no noise publishes.
- **Lock file commit-back (like `.env.lock`)**: CI produces the version, commits state back to repo. The repo is the source of truth — `git log` at any commit shows exactly which package versions that code ran against.
- **Cesium-unity excluded**: Different lifecycle (manual trigger, upstream version, 30-60 min build). Can reuse the manifest-update mechanism later.
- **Hash scope**: NuGet = all `.cs` files in `packages/generated/csharp/api-client/src/PlaceframeApiClient/` (excluding `.csproj`, which is regenerated with a fixed version). UPM = all files in the package directory except `package.json` (which contains the version field being bumped). Hash is deterministic: sort file paths, hash contents, combine.
- **CI loop prevention**: `paths-ignore` for the state file, same proven pattern as `.env.lock` with `paths-ignore: [".env.lock"]` in `build-docker.yml`.
- **Core declares `org.nuget.placeframeapiclient` as a dependency**: The `file:` reference in the Placeframe workspace manifest (`com.placeframe.api-client`) is a holdover from before registries were set up. The API client is auto-generated — nobody hand-edits it. Switching to the registry reference (`org.nuget.placeframeapiclient` from UnityNuGet) eliminates the dual identity problem. Core's `package.json` declares it as a dependency, consumers get it transitively. UnityNuGet presents NuGet packages as UPM packages — from Unity's resolver perspective, `org.nuget.placeframeapiclient` is a regular UPM package served by the UnityNuGet scoped registry. Consumer projects just need the UnityNuGet scoped registry configured (which they already do).
- **NuGet API key for now, OIDC later (T87)**: NuGet.org's OIDC trusted publishing is in gradual rollout and not yet available on the `tylerhatch` account. Using a traditional `NUGET_API_KEY` repository secret until the feature is available. T87 tracks the switch to OIDC.
- **Monorepo consumers use `file:` references**: Local developers get immediate iteration without publishing. Trade-off: no transitive dependency resolution (must list all dependencies explicitly in each consumer manifest). Acceptable for 3-4 internal packages. See "Monorepo consumer strategy" in Context for full analysis. Unity's package manager has no workspace protocol equivalent — this is a fundamental limitation, not a gap in our approach.
- **No dedicated integration test project**: Ditched. The "single commit-back target" simplification didn't hold up — CI would still need to update multiple `package.json` files. The testing gap (nothing exercises registry resolution) is accepted as a trade-off. Registry resolution is validated implicitly when external consumers use the packages.
- **Uniform state file format (version + hash per package)**: `publish-state.json` stores `{ "version": "x.y.z", "hash": "abc..." }` for every package uniformly. Duplicates the version that's already in UPM `package.json` files, but keeps the format simple and gives NuGet (whose `.csproj` is regenerated) a persistent version home. CI writes both state file and `package.json` atomically.

## Approach

Content-hash each package's source directory, compare against `publish-state.json`, auto-bump patch and publish when content differs. Cascade dependency graph: NuGet → Core → ARFoundation/MagicLeap. Commit state + updated `package.json` files back to repo. NuGet publishes via OIDC trusted publishing (same pattern as npm). Loop prevention via `paths-ignore` on all CI-written files.
