# OpenAPI generator emits empty `_auth_settings` on every operation; `access_token` is dead

**Severity**: medium — auth pattern documented by `placeframe_api_client.Configuration(access_token=...)` is silently a no-op for every consumer. Every script and service that talks to the API has to ship a manual default-header workaround.

**Location**: Generator config / templates that drive `uv run generate-clients --config build/openapi-projects.json`. Symptom is visible at every operation method in `packages/generated/python/api-client/placeframe_api_client/api/default_api.py` (and its C#/localizer/zed-capture siblings) — e.g. lines 385-398 emit `_auth_settings: List[str] = []` then pass that empty list to `param_serialize`. The local workaround lives at `scripts/src/scripts/api_auth.py:18-23`, which mutates `api_client.default_headers["Authorization"]` directly.

**Symptom**: A consumer that follows the openapi-generator convention — `Configuration(access_token=my_token)` or `Configuration(api_key={"...": my_token})` — gets no `Authorization` header on outgoing requests, because `Configuration.auth_settings()` returns `{}` and every operation's `_auth_settings` list is empty. Requests go out anonymous; the API returns 401. The failure is silent at codegen time and discoverable only by running the generated client.

**Mechanism**: The OpenAPI specs dumped by the Litestar apps do not declare a `securitySchemes` section that the generator can attach to each operation. With no schemes declared, openapi-generator's Python template emits `_auth_settings: List[str] = []` for every method. The generated `Configuration` class still accepts `access_token` (it's part of the boilerplate), but since no operation references any auth scheme by name, the value never reaches a request header.

**Fix sketch**: Declare an OpenAPI `securitySchemes` entry in each Litestar app's spec — for our flow, an OAuth2 bearer scheme — and mark each protected operation with `security: [{<scheme>: []}]`. Litestar exposes this via app-level `security` or per-route `security` config; setting it once on the app pushes it onto every operation. After re-running `uv run generate-clients`, the generated `_auth_settings` lists become non-empty, `Configuration(access_token=...)` starts injecting the `Authorization` header automatically, and `scripts/src/scripts/api_auth.py:18-23`'s `cast(dict[str, str], api_client.default_headers)["Authorization"] = ...` workaround can be deleted (or downgraded to a fallback). The same fix lights up auth for the C# clients (Unity), the localizer client, and any future consumer for free.

**Verification**: After regenerating clients, grep `packages/generated/python/api-client/placeframe_api_client/api/default_api.py` for `_auth_settings: List[str] = \[\s*\]` — expect zero hits on protected operations. Then construct `DefaultApi` with `Configuration(access_token=token)` (no manual header injection) and confirm a protected call returns 200, not 401. `scripts/SPEC.md:144` mentions the workaround — once removed, update that paragraph too.
