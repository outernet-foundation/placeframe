# Capture-tool upload abandons on the first transient HTTP failure; existing Polly retry hook is unused

**Severity**: medium — a single TCP/TLS reset mid-upload strands the capture in `clientPhase=Failed` and requires manual user "Retry" tap. Symptom amplifies under concurrent uploads through ngrok where mid-stream resets are routine.

**Location**:
- `apps/AndroidMobile/Assets/Scripts/Capture/CaptureRow.cs:82-171` — `Upload(CaptureState capture)`. `CreateCaptureSessionAsync` is called exactly once inside the outer `try`; any throw flips `clientPhase` to `Failed` and rethrows.
- `packages/generated/csharp/api-client/src/PlaceframeApiClient/Client/ApiClient.cs:532-548` — generator-provided Polly hook: if `RetryConfiguration.AsyncRetryPolicy != null`, every `SendAsync` is wrapped with `ExecuteAndCaptureAsync`. Otherwise (today's path) `SendAsync` runs unwrapped.
- `packages/generated/csharp/api-client/src/PlaceframeApiClient/Client/RetryConfiguration.cs` — static slot holding `RetryPolicy` / `AsyncRetryPolicy`. Both are `null` by default and never assigned anywhere under `apps/AndroidMobile/` or `packages/unity/` (`grep -rn "RetryConfiguration\." /placeframe/apps /placeframe/packages/unity` returns no consumers).
- `packages/unity/Placeframe/Assets/Packages/Polly.7.2.3/` — Polly 7.2.3 NuGet is already bundled, so wiring is config-only; no new dependency is required.

**Symptom (observed 2026-05-31 03:20:19 UTC)**: Three captures uploaded in parallel from the AndroidMobile tool through the ngrok tunnel (`skilled-finally-primate.ngrok-free.app`). One — `aacad6a9-2eb3-4bf4-9aa3-6264a86506a0`, request id `50bd8be8276d410884a8eae1e7f4a846`, body 37,970,700 B — threw `System.Net.Http.HttpRequestException: An error occurred while sending the request` 3.5 s in (well before the body finished streaming) at the `PlaceframeApiClient.Api.DefaultApi.CreateCaptureSessionAsync` frame. The other two (`4bd303f1…` 37 MB, `17af01a0…` 53 MB) finished cleanly ~35-40 s later. The failed capture's row sat as `Failed` in the UI; no retry attempt was made. Server-side the API logged only the two successful POSTs — no fourth request ever arrived.

**Mechanism**: A mid-stream TCP/TLS reset on the third concurrent ngrok upload (free-tier tunnel + contention with two other large POSTs is the prime suspect) surfaces as `HttpRequestException` deep inside `_httpClient.SendAsync`. The generated client propagates it untouched because the Polly hook is dormant. `Upload(CaptureState)` catches `Exception`, logs `"Upload failed …"`, sets `clientPhase=Failed`, and rethrows. There is no bounded retry, no backoff, no idempotency-key-based replay. The Loki sink swallowed the inner-exception structure separately due to the null-scalar serialization bug fixed in `8775a172` — that is unrelated to the retry gap but is what made the exception detail invisible in the original incident logs.

**Fix sketch**: The right shape is two-tiered.

1. **Configure `RetryConfiguration.AsyncRetryPolicy` at app startup** (`apps/AndroidMobile/Assets/Scripts/Capture/App.cs` is the natural site, near where `VisualPositioningSystem.Api` is constructed). A Polly `AsyncPolicy<HttpResponseMessage>` that retries `HttpRequestException` and 5xx responses with bounded exponential backoff (e.g. 3 attempts, base 1 s, full jitter) closes the gap for every API call — `CreateReconstruction`, `CreateLocalizationMap`, status polling, `RetryReconstruction`, etc. None of those have replayability concerns because their request bodies are tiny JSON.
2. **Special-case the upload.** `CreateCaptureSessionAsync`'s body wraps `LengthOnlyStream(response.Data.Content, …)` (see `apps/AndroidMobile/Assets/Scripts/Capture/ZedCaptureController.cs:191-199` and `packages/generated/csharp/api-client/src/PlaceframeApiClient/Client/FileParameter.cs`) — the ZED-box HTTP response stream is **not** seekable. A naive global Polly retry would replay an exhausted stream on attempt 2 and POST an empty body, which is worse than today's behavior. Two options:
   - **(a) Excluded + call-site retry.** Configure the global policy to skip when the request body is non-seekable (check `req.Content` shape, or scope the policy via a per-request marker), and wrap the `await Api.CreateCaptureSessionAsync(...)` call in `Upload(CaptureState)` with a bespoke retry that re-fetches `ZedCaptureController.GetCapture(id)` / `CaptureManager.GetCaptureTar(id)` on each attempt to get a fresh stream. Cleaner separation; upload remains one explicit special case. The retry shape must live in its own helper (per the no-nested-try rule in `CLAUDE.md`).
   - **(b) Buffered upload body.** Pre-buffer the upload bytes into a `MemoryStream` once and rewind on retry; then the global Polly policy handles upload too with no special case. Costs ~37–53 MB of phone heap during each upload (peak doubles in-flight bytes). Phones tolerate it, but the buffering is a behavior change worth being explicit about.

  Recommendation: (a). Smaller blast radius, makes the upload's replay semantics explicit at the only call site that actually needs them, and doesn't add per-upload memory pressure.

**Verification**: Three checks.
1. **Unit-level**: With a Polly policy installed, hit `Reconstruct(capture)` / `CreateMap(capture)` against an API endpoint that 503s on the first request and 200s on the second; both should ultimately succeed and a single retry should be logged.
2. **Upload retry**: Simulate a mid-stream transport failure on the first upload attempt (e.g. set ZED-box `aoa-bridge` to close the underlying socket on the first byte range of `/capture_sessions`, or just kill ngrok briefly while three uploads are in flight). The Loki capture-tool stream should show `Upload transport failure capture=… attempt=1 … retrying after Xms` followed by a successful second attempt. The server should see exactly one `201 Created` for that `capture_session_id` (idempotency via the explicit `id` query parameter on `POST /capture_sessions`).
3. **No regression on bad bodies**: A 4xx (malformed payload, auth failure) must NOT retry. Verify by submitting an upload with an invalid token; expect a single attempt, no retry log lines.

**Notes for the future implementer**:
- Per `apps/AndroidMobile/CLAUDE.md`, the AndroidMobile tool's HTTP path is split: AOA traffic uses the Java+OkHttp `AndroidAoaHttpHandler`; internet-bound traffic uses .NET's default `HttpClientHandler`. The Polly hook in the generated `ApiClient` wraps `_httpClient.SendAsync` and is therefore agnostic to which handler is plumbed in — both paths benefit. Confirm by checking that the policy fires regardless of whether the call goes to the ngrok-fronted API or the AOA-fronted ZED.
- Idempotency. The current `POST /capture_sessions` accepts an explicit `id` query parameter — see `apps/AndroidMobile/Assets/Scripts/Capture/CaptureRow.cs:143`. Confirm the server returns a deterministic response (200 / 409 / 201) when the same id is POSTed twice with the same body; if it raises a unique-key violation that surfaces as 5xx, the retry policy will fight it. Worth a quick server-side audit before lighting up retries.
- The current `Upload` method's outer `try/catch (Exception ex)` should narrow to the specific exogenous types (`HttpRequestException`, `TaskCanceledException` from timeout, `OperationCanceledException` from user cancel) per the `CLAUDE.md` "Don't catch what you can't handle" rule. Cancellation must not be retried.
