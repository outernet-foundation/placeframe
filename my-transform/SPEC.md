# Compose → Kubernetes transform

## What this is

`my-transform/` is a [Docker Compose Bridge](https://docs.docker.com/compose/bridge/) transformer: a set of Go `text/template` files, packaged in an image, that `docker compose bridge convert` runs over the merged `compose.yml` model to emit Kubernetes manifests under `out/`. It is the mechanism that turns the self-hosted server stack (the same services `uv run up` runs under Docker) into a Kustomize tree that `kubectl apply -k` can deploy to a cluster. The `uv run generate-k3s` command (`packages/python/placeframe-stack/src/placeframe_stack/generate_k3s.py`) drives the whole pipeline and post-processes the output; `out/` is a committed, byte-stable artifact regenerated by that command.

## Shape

Two layers, both templated:

- `templates/base/` — one template per Kubernetes resource kind (`deployment.tmpl`, `service.tmpl`, `persistentVolumeClaim.tmpl`, `secret.tmpl`, `configmap.tmpl`, `namespace.tmpl`, `networkpolicy.tmpl`, `rbac.tmpl`, `expose.tmpl`). Each ranges over `.services` / `.volumes` / `.secrets` from the compose model and emits `out/base/`. `deployment.tmpl` also renders Jobs (for `restart: "no"` services), init-container waits from `depends_on`, and the `wait-for` ServiceAccount/Role/RoleBinding when any service waits on a `service_completed_successfully` dependency.
- `templates/overlays/desktop/` and `templates/overlays/model-runner/` — Kustomize overlays emitted to `out/overlays/*`. The desktop overlay patches PVCs onto the `hostpath` storage class and re-shapes published services for Docker Desktop.

`_index.tmpl` in each layer emits that layer's `kustomization.yaml`.

The full pipeline (`generate_k3s.py`):

    docker build my-transform  -->  compose bridge convert  -->  port-sort + runAsUser normalize  -->  inject secretGenerator
         (transformer image)          (writes out/)            (YAML round-trip, per manifest)        (into out/base/kustomization.yaml)

Deploy: run `uv run generate-k3s` on a host holding the target `.env`, then `kubectl apply -k out/base` (cluster-default storage) or `kubectl apply -k out/overlays/desktop` (Docker Desktop).

## Constraints

### The template function set is custom, not Sprig

The transformer registers a bespoke function map (`safe`, `indent`, `base64`, `title`, `uppercase`, `seconds`, `truncate`, `join`, `portName`, `isString`, `hasAttribute`, `getAttribute`). Some names overlap Sprig (`indent`, `title`, `join`) but the set is **not** Sprig — `splitList`, `dict`, `set`, `hasKey`, and `atoi` are all absent and fail the build with `function "X" not defined`. Any transform step that needs string splitting or a mutable set cannot be done in a template. Two consequences below (runAsUser, PVC dedup) exist because of this.

### Environment-sourced secrets are materialized by `generate_k3s.py`, not by a template

compose-bridge's secret template only renders a `Secret` when the compose secret carries inline `content`. This stack's secrets are `environment:`-sourced (`compose.yml` `secrets:` block → `DATABASE_*_PASSWORD`, `MINIO_SECRET_KEY`), so the transformer emits **nothing** for them, leaving the Deployments referencing Secrets that do not exist. `_generate_secrets` in `generate_k3s.py` closes this: it reads the compose secret→env-var mapping, materializes each value from the merged `.env`/`.env.lock`/`.env.shas` into `out/base/.secrets/<name>` (gitignored via the root `.gitignore` `.secrets` entry), and injects a Kustomize `secretGenerator` into `out/base/kustomization.yaml`. This mirrors how the compose stack sources the same values from `.env` and keeps secret values out of the committed tree.

This work cannot live in a template because compose-bridge hands `_index.tmpl` only the list of emitted file descriptors — not `.secrets` or `.services` — so a template has no access to the secret definitions when writing `kustomization.yaml`.

`generatorOptions.disableNameSuffixHash: true` is set so the generated Secret names match the static `secretName:` references in the Deployments. The trade-off: a changed secret does not roll the consuming pods (matching compose semantics, where a secret change also requires a manual restart).

### `enableServiceLinks: false` on every pod

Kubernetes injects Docker-link-style env vars for every Service (`POSTGRES_PORT=tcp://10.43.x.x:5432`, `<SVC>_SERVICE_HOST`, …). These collide with the stack's own config: the app reads `POSTGRES_PORT` expecting `5432` and gets a `tcp://…` URL, which crashes `create-database` at `int(POSTGRES_PORT)`. Compose never injects these, so every pod template in `deployment.tmpl` sets `enableServiceLinks: false` to match compose semantics.

### Internally-addressed services must declare `expose`

`expose.tmpl` emits a ClusterIP Service (named for the service, e.g. `api`) only when the compose service declares `ports` or `expose`; `service.tmpl` separately emits a `<name>-published` Service only for host-published `ports`. Docker's network resolves any service name regardless of `expose`, but Kubernetes needs a Service object for DNS. So a service that others reach by name yet publishes nothing to the host must still declare `expose` or it gets no Service and its DNS name never resolves. `api` (the gateway's `reverse_proxy api:8000`, and callers hitting `http://api:8000`) and `lease-server` (`http://lease-server:8000`) therefore declare `expose: ["8000"]` in `compose.yml` — harmless to the Docker stack, load-bearing for the Kubernetes one.

### One PVC per named volume, shared across services

compose volumes are shared: `initialize-cloudbeaver` and `create-database` seed `cloudbeaver_data`, then `cloudbeaver` serves it; `initialize-loki` chowns `loki_data`, then `loki` uses it. `persistentVolumeClaim.tmpl` therefore emits exactly one PVC per named volume (named for the volume, e.g. `cloudbeaver-data`), and `deployment.tmpl` points every consumer's `claimName` at that shared name. Deduplication is done without a set: the template emits the PVC only from the lexicographically-first service that mounts the volume (`lt $otherName $name` over `.services`, which Go ranges in sorted key order).

The shared PVCs are `ReadWriteOnce`. This targets a single-node cluster: the seeding Jobs run to completion — enforced by the `depends_on` init-container waits `deployment.tmpl` generates — before the serving Deployment mounts the volume, so the reader and writers never contend. On a multi-node cluster the RWO claim plus node affinity would need revisiting.

### Python post-processing normalizes what templates can't

`generate_k3s.py` round-trips every emitted manifest through PyYAML for two reasons that also shape the output:

- **Byte-stability.** compose-bridge derives container/Service ports from the image's `ExposedPorts`, a Go map whose iteration order is randomized, so ports come out shuffled run-to-run. `_sort_ports` sorts every ports list so a clean-tree check on `out/` is meaningful. The round-trip also strips YAML comments, so the `# Generated code, do not edit` line in the templates never reaches `out/`.
- **`runAsUser`.** compose `user: "uid:gid"` reaches the template as one string and is emitted verbatim, but Kubernetes requires an integer `runAsUser`/`runAsGroup`. `_normalize_run_as_user` splits the pair (string splitting being unavailable in the template engine). A non-numeric user raises rather than emitting an invalid manifest.

### Healthcheck `CMD` probes must be argv, not a joined string

compose `test: ["CMD", "curl", "-f", "<url>"]` maps to a Kubernetes `exec` liveness probe. The command must be a YAML sequence (`["curl","-f","<url>"]`); a single joined string makes kubelet try to `exec` a binary literally named `curl -f <url>`. `deployment.tmpl` ranges the test entries and emits each (skipping index 0, the `CMD` sentinel) as its own list item. `CMD-SHELL` tests are instead wrapped in `/bin/sh -c`.

### The transformer base image is digest-pinned

`Dockerfile` pins `docker/compose-bridge-transformer` by `@sha256:` digest, per the repo-wide no-moving-references rule. Bump it deliberately; the emitted manifests depend on the transformer's built-in behavior for anything the templates don't override.
