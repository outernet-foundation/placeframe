# Placeframe Dashboard

## Summary

Built the v1 dashboard at `placeframe/dashboard/`:

**`howard_test.py`** (`scripts/src/scripts/howard_test.py`) — added `--json` output to `captures`, `reconstructions`, `show`, `reconstruct`, `visualize`; added local caching (`show --cache` and `reconstruct`'s `--wait` path download the reconstruction tar to `data/reconstructions/<id>.tar` once it succeeds; `visualize` reads from that cache first and defaults its PNG there too — confirmed this cuts a repeat visualize from ~40-60s down to ~1.6s).

**`dashboard/backend/`** — standalone Litestar app (own `.venv`, not part of the placeframe uv workspace) on port 8010. Every route shells out to `uv run howard-test ... --json` with cwd pinned to the placeframe repo root. `POST /api/reconstruct` returns a job id immediately (after the fast "create" call), then a background task polls `show --cache` every 3s until terminal status — so the tar gets cached automatically as soon as a reconstruction succeeds, before anyone even clicks "Create PNG". `POST /api/visualize` is the same fire-and-poll shape. `GET /api/jobs/{id}` is what the frontend polls.

**`dashboard/frontend/`** — Vite + React + TypeScript on port 5174. Reconstruct tab (capture list → dialog with capture picker + options JSON → live job status banner) and Visualize tab (reconstruction list → Create PNG / Interactive / View → inline point-cloud image).

**Interactive viewer** (`dashboard/frontend/src/viewer/`) — the "Interactive" button opens `/viewer?reconstruction=<id>` in a new window: a three.js point-cloud viewer modeled on CloudCompare's mouse scheme.
- `howard-test points <id>` (new CLI command) writes raw binary to stdout, reusing `_fetch_reconstruction_geometry`'s cache-first logic: `point_count:u32, positions:f32[n*3], colors:u8[n*3], pose_count:u32, pose_positions:f32[m*3], pose_orientations(xyzw):f32[m*4]`. `dashboard/backend`'s `GET /api/reconstructions/{id}/points` passes those bytes straight through; the frontend parses them directly with `DataView`/typed-array views, no JSON round trip.
- The point cloud, camera poses, RGB world axes (`THREE.ArrowHelper` x3), and rotation gizmo are all fixed in world space; **the camera orbits/pans/dollies**, not the object. (An earlier version rotated the object in front of a fixed camera — that left whichever axis pointed along the fixed view direction permanently foreshorted to a dot, no matter how you rotated. Orbiting the camera instead, with orientation stored as a single quaternion updated only by incremental premultiplies — never converted to Euler/az-el — means every axis is inspectable from some angle and there's no gimbal-lock singularity, so the XY/XZ/YZ preset buttons can set exact axis-aligned views.)
- Left-drag orbits (gizmo sphere + 3 great circles, each colored by the axis it's a rotation indicator for, shown for the duration of the drag); right-drag pans; wheel/trackpad zooms (dolly).
- Recenter restores the initial oblique orientation/pan/zoom computed at load (median-center + 90th-percentile-radius framing, same robust-framing rationale as the static PNG renderer).
- **Axis convention**: reconstruction data is raw OPENCV-world (+Y physically *down* — confirmed against the ZED capture pipeline's `COORDINATE_SYSTEM.IMAGE` init and the reconstructor's gravity alignment to world `[0,1,0]`) and stays untouched end to end; there's no data transform anywhere in the pipeline. Only the camera's default/recenter orientation (`buildDefaultOrientation` in `PointCloudScene.ts`) is chosen so the initial view reads correctly, with world `-Y` (true physical up) rendered toward the top of the screen. A camera pose is upright/normal when its local +Y arrow (Arrows mode) points the *same* screen direction as the world's green Y axis (both point toward the physical floor) — verified against this dataset's actual poses (100% of 257 frames show that alignment, i.e. the capture device was held normally throughout).
- Capture reads the canvas via `toDataURL` (`preserveDrawingBuffer: true` on the renderer) and POSTs to `POST /api/screenshots`, which sanitizes the plot title and writes to `data/reconstructions/<title>/<title>_captureN.png` with `N` computed by scanning the folder for the next unused integer.
- Plot title is editable via a small dialog; defaults to the reconstruction id.
- **Camera poses**: `sfm_model/frame_poses.npz` (sibling of `points3D.npz` in the same cached tar) holds one `world_from_rig` pose per registered *rig frame* — not per camera image, so a multi-camera rig (e.g. the stereo ZED) contributes half as many poses as images. A "Camera" dropdown switches between **Frustum** (wireframe pyramid per pose, apex at the camera center, oriented via the pose quaternion in OpenCV camera-space X-right/Y-down/Z-forward) and **Arrows** (a tiny per-pose RGB axis triad, same color convention as the world axes) — both built once at load as merged `LineSegments` geometries (one draw call each) and toggled by visibility, plus **Off**. A trajectory polyline through the poses in array order is shown whenever Camera mode isn't Off.
- A "Points" dropdown controls the point cloud's marker size (levels 1-10, each level = `cloudRadius * 0.002 * level`, default 2) or **Off** to hide the cloud entirely — useful for inspecting the camera trajectory/frustums in isolation on a dense cloud.
- **Frame-number labels**: every `LABEL_EVERY_N` (10th) pose gets its array-index number rendered above it as a `THREE.Sprite` with `sizeAttenuation: false` — sprite `scale` is then a screen-space, not world-space/perspective, size, so labels stay a constant on-screen size at any zoom level (verified: identical pixel size zoomed all the way in vs. the default view). This has to be an actual scene object, not a DOM/CSS overlay (e.g. `CSS2DRenderer`), because "Capture" screenshots the WebGL canvas directly via `toDataURL` — a DOM overlay wouldn't appear in the exported PNG. Labels are plain halo-outlined text (white stroke behind dark fill, no filled badge shape) to stay legible over both the point cloud and the light background without adding visual weight, since the capture trajectory often loops back near itself and dense label clusters were the main risk. The other 9-in-10 poses are dimmed — blended `72%` toward the scene's background color, not darkened, since darkening a bright marker color on a *light* background reads as **more** prominent, the opposite of "dim" — via per-vertex colors on the same merged frustum/arrow geometries (no extra draw calls).

Verified end-to-end in the browser: capture list loads, dialog opens, reconstructions list shows live status for an in-flight job (`queued` → `matching_features` → `reconstructing`, tracked via a real background reconstruction), "View" renders the cached PNG inline, and the interactive viewer's rotate/pan/zoom/plane-views/recenter/title-edit/capture/camera-mode-dropdown/point-size-dropdown were each exercised directly in Chrome (including dispatching synthetic pointer/wheel/select-change events, since the browser-automation tool's built-in scroll gesture and native `<select>` popups don't interact reliably with the canvas/DOM directly).

**Localize tab** — ingests a directory of query images, estimates each image's pose against a reconstruction's map, and surfaces the results as a table with per-row thumbnails.
- `howard-test localize <reconstruction_id> <image_dir>` (new CLI command) is the orchestration entry point. There is no standalone reusable localization module elsewhere in the repo — `scripts/fit_calibration.py` is the only other caller of the localizer API, and this command follows its exact calling pattern rather than introducing a new abstraction. For each image: reads the reconstruction's capture session manifest to get `PinholeCameraConfig`/`AxisConvention`, gets-or-creates an identity-anchored `LocalizationMap` for the reconstruction (`get_reconstruction_localization_map`, falling back to `create_localization_map` on 404), and calls `api.localize_image`. The API returns `camera_from_map_transform` (world-to-camera extrinsic); the command inverts it (`R.T`, `-R.T @ t`) to get the camera's position/orientation *in* the map/world frame — the same convention `frame_poses.npz` uses, which is what makes the pose overlay in the viewer below a drop-in reuse of the existing frustum-rendering code. Results (position, quaternion, roll/pitch/yaw in degrees, a small JPEG thumbnail as a data URI) are written to `data/localizations/<run_id>/results.json`, keyed by a fresh `run_id` per invocation. `howard-test localize-save-table <run_id> <csv_path>` and `howard-test localize-save-images <run_id> <output_dir>` (pose text burned into the image's upper-left corner via Pillow) both read that same `results.json` back — no re-localization needed to export.
- `dashboard/backend`: `POST /api/localize` is the same fire-and-poll job shape as reconstruct/visualize (shells out to `howard-test localize ... --json`, which only returns once *all* images in the directory are localized). `GET /api/localizations/{run_id}` reads `results.json` directly off disk (no subprocess — same pattern as the cached-PNG route) so re-opening a past run's table is instant. `POST /api/localizations/{run_id}/save-table` and `.../save-images` are thin subprocess wrappers around the two CLI export commands.
- `dashboard/frontend`'s Localize tab: pick a succeeded reconstruction from a dropdown, type a server-local image directory path, Run. Once the job succeeds, the results table shows index/thumbnail/filename/status/XYZ/RPY per image (failed localizations show their error message spanning the pose columns instead). "Save table" and "Save images" open a small dialog for a server-local output path and call the corresponding backend route. "Save table"/"Save images" (like the image directory input) take typed local filesystem paths, not a file-picker — the dashboard always runs against the same machine as the CLI it wraps, so there's no upload/download boundary to cross.
- **"Visualize poses"** opens `/viewer?reconstruction=<id>&localization=<run_id>` — the *same* interactive viewer built for reconstructions, not a separate view. `ViewerPage` fetches the localization result after the point cloud loads, filters to images with `status: "ok"`, and calls a new `PointCloudScene.setLocalizedPoses(positions, orientations, count)` method that reuses `buildCameraFrustums` (now parameterized by `color` and a `highlightEvery` interval, previously hardcoded to the reconstruction's orange/every-10th-highlighted scheme) with a distinct purple (`0x9c27b0`) and `highlightEvery: 1` — every localized pose is fully bright and labeled, unlike the dimmed majority of the reconstruction's own (usually much longer) trajectory. Positions are recentered using the *same* median-center offset `setPoints` already computed (stored on the scene as `recenterOffset`), so the overlay lines up with the already-recentered cloud/reconstruction-poses without recomputing anything. The overlay is independent of the "Camera" dropdown (which only toggles the reconstruction's own frustums/arrows/trajectory/labels) — localized poses stay visible regardless, since they're a separate, typically much smaller dataset the user explicitly asked to see. Verified in the browser: localized a 3-image directory, table populated with thumbnails and poses matching a prior CLI-only run bit-for-bit, "Save table"/"Save images" dialogs wrote real files, and "Visualize poses" rendered 3 purple frustums (one nearly coincident with the reconstruction's own frame 0, as expected — that query image *is* the capture's first frame) alongside the existing orange trajectory, toggleable independently via the Camera dropdown.

**Localize progress bar**: the "Localizing…" banner now shows a fill bar plus "n out of N images" text, updated live as the run progresses. Since `howard-test localize` only returns once every image is done, per-image progress needed a side channel outside the blocking subprocess call: the CLI's `localize` command now generates (or accepts via a new `--run-id` option) the run id *before* starting the async localization loop, creates `data/localizations/<run_id>/` immediately, and writes `progress.json` (`{"completed": n, "total": N}`) right away and again after every image (`_localize`'s loop now takes a `report_progress: Callable[[int], None]` callback, called after each `_localize_one_image`). `dashboard/backend`'s `POST /api/localize` generates the run id itself (rather than waiting for it to come back in the CLI's final JSON), passes it through as `--run-id`, and returns `{job_id, run_id}` immediately so the frontend can start polling `GET /api/localizations/{run_id}/progress` (a plain `progress.json` file read, defaulting to `{completed: 0, total: 0}` if the file doesn't exist yet — the brief window right after the job is spawned) from the very first tick. `dashboard/frontend`'s new `useLocalizationProgress` hook (mirroring the existing `useJobPoll` hook) polls that endpoint once a second while the job is running. Verified end-to-end: `progress.json` observed going `{completed:0,total:3}` → `{completed:1,total:3}` → `{completed:2,total:3}` → `{completed:3,total:3}` via direct polling, and the UI's "0 out of 3 images" state confirmed live in the browser at job start.

**Image-directory Browse button**: the Localize tab's image-directory field has a "Browse…" button next to it, backed by a new `GET /api/browse-directories?path=<path>` route (`dashboard/backend/app.py`) and a `DirectoryBrowserDialog` component (`dashboard/frontend/src/components/DirectoryBrowserDialog.tsx`). This is a server-local filesystem browser, not a native `<input type=file webkitdirectory>` picker — a native picker can't be used here because browsers never expose the absolute path of a picked directory (only a `File` list with paths relative to the picked root), and the CLI this dashboard shells out to needs a real absolute path. Since the dashboard always runs on the same machine as `howard-test`, walking the real filesystem server-side (starting at the server's home directory, `..`-up and click-to-descend navigation, directories only, hidden dotfiles excluded) and returning absolute paths is the direct equivalent of a native picker. Verified in the browser: opened the dialog, navigated `/home/<user>` → `/` → `/tmp` → `/tmp/localize-test-images`, hit "Select this folder", and the image-directory input was populated with the exact path.

## Key decisions (from the clarifying-questions round)

- **Location**: inside the placeframe repo, in `dashboard/`, not a separate sibling repo — so it always runs against this checkout's `uv run howard-test` and `.env` with no path configuration.
- **Tech stack**: lighter, no Docker — Litestar backend + Vite/React/TS frontend, run directly via `uv run` / `npm run dev`, no Postgres/containers. Can containerize later once the shape settles.
- **Long jobs**: fire-and-poll — backend kicks off the CLI command in the background and returns immediately; frontend polls a status endpoint for live progress.
- **Local caching**: yes — `reconstruct` downloads/keeps the finished reconstruction tar at `data/reconstructions/<id>.tar`; `visualize` reads from that cache when present and writes its PNG there too.

## Running it

Both dev servers run independently, outside Docker:

```bash
cd dashboard/backend && uv run uvicorn app:app --reload --port 8010
cd dashboard/frontend && npm run dev   # http://localhost:5174
```

`dashboard/backend` is a standalone `uv` project (its own `pyproject.toml`, `.venv`) — not a member of the root placeframe uv workspace — specifically so it doesn't get swept into `uv sync --all-packages`, `lock-python`, `preflight`, or codegen. It only needs `litestar` + `uvicorn`.

`data/`, `dashboard/backend/.venv/`, `dashboard/backend/__pycache__/`, `dashboard/frontend/node_modules/`, and `dashboard/frontend/dist/` are all gitignored.

## Not yet built

- **Odometry drift correction**: absolute-pose-estimate correction of odometry drift, surfaced in the interactive viewer as "raw" vs "corrected" poses/point clouds. Not started.
- **Capture upload UI**: the Reconstruct tab only lists and reconstructs *existing* server-side captures; there's no dashboard flow yet for uploading a new capture tar (the CLI's `upload`/`run` commands still work standalone, just aren't wired into the UI).
