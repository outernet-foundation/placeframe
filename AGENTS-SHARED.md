# Shared Agent Conventions

Repo-agnostic conventions — how we build software, independent of any one project. The counterpart `AGENTS.md` holds the repo-specific guidance (what this project is, how to operate it); this file holds everything that would apply equally in another repo, even one that doesn't exist yet.

This file is required reading, loaded two ways so it works in both agent runtimes: Claude Code pulls it in via an `@AGENTS-SHARED.md` import in the root `AGENTS.md` (reached through the root `CLAUDE.md`, whose one line is `@AGENTS.md`); opencode loads it via an `instructions` entry in `opencode.json`. Both always-load it — the split from `AGENTS.md` is conceptual, not a lazy-load optimization.

## Recommending fixes

- **Default to the architecturally correct change, not the smallest one.** Lead with the structural fix for the underlying design weakness — even when its blast radius is large or it needs a substantial refactor. Don't pre-filter by implementation cost; surface the correct shape and let the user choose a smaller scope, rather than pre-making that tradeoff for them. Treat phrases like "minimum viable," "let's start small," "bandaid for now," or "surgical fix" as signals that you're silently downgrading the recommendation — and when the bigger fix feels intimidating, that's exactly when to recommend it.

## Commit discipline

- **Commit on yield, not mid-work.** When working autonomously on a task, make all changes first, then commit once before returning control to the user. Do not create multiple commits in a row on the same task. The only reason to split is when dirty files belong to different tasks, or when prose and code are both dirty (see below).
- **Prose and code go in different commits.** Markdown prose (`AGENTS.md`, `AGENTS-SHARED.md`, `README.md`, style guides, any `*.md`) and source code (`.py`, `.cs`, `.ts`, `.sql`, configs, etc.) belong in separate commits, even when changed together. Prose-first or code-first ordering doesn't matter; the constraint is that the two never share a commit. This keeps prose diffs reviewable on their own terms.
- **Spec-first on disagreement.** When an agent-facing doc and the code it describes disagree, update the doc first to reflect the *intended* state, surface the diff, *then* change the code. This converts every disagreement from silent rot into an explicit human decision.
- **No trailers.** NEVER add `Co-Authored-By`, `Signed-off-by`, or any other trailers to commit messages.
- **Reviewable commit format.** Subject line under 72 characters — concise but specific; name the actual things that changed, don't hide details behind vague catch-alls like "update config" or "fix scripts." Optional body as a bulleted list (`-`) of short phrases stating *what* changed, not *why* — no full sentences, no parenthetical justifications. Err heavily toward terse. No prefixes — no `[prose]`, `[code]`, `[Tn]`, or other bracket tags.
- **Squashing commits: use `--fixup` + `--autosquash`.** When squashing a commit into an earlier one, use `git commit --fixup=<sha>` then `GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash <sha>~1`. Do not hand-edit rebase todo files with sed/awk `GIT_SEQUENCE_EDITOR` scripts — the todo format is fragile and causes silent no-ops or dropped commits.
- **Verify the target is branch-local before fixup.** Run `git merge-base --is-ancestor <target-sha> <integration-branch>` before `git commit --fixup=<target-sha>`. If it returns 0, `<target-sha>` is on shared upstream history and `git rebase -i --autosquash <target-sha>~1` will rewrite every commit since — silently breaking alignment with origin. When the target is upstream, skip the fixup and make a regular new commit instead.
- **New branches, not renames.** When asked to put work on a new branch name, use `git checkout -b <new-name>` to create a fresh branch from the current HEAD. Never use `git branch -m` to rename — it breaks upstream tracking for anyone who already has the old branch.

## Communication

- **Report all errors on handoff.** Whenever returning control to the user after a task, list every error encountered during execution and how it was resolved. No silent workarounds.
- **Diagnose first, fix only when asked.** When encountering any failure — CI errors, test failures, runtime exceptions, "what happened?" questions — default to root-cause analysis, not fixing. Present the diagnosis and yield. Only fix after the user directs the fix. This applies whether the user says "what happened?", reports an error, or pastes a failing log.
- **Yield after answering questions.** When the user asks a question mid-task, answer it and stop. Do not interpret the answer as an implicit instruction to continue executing.

## Trackable work

- **Linear is canonical for trackable work** (bugs, features, chores, refactors, initiatives). Use the audited `linear` CLI as the write path — it keeps every ticket and project write transparent, reviewable, and on-convention. Don't hand-write GraphQL mutations and don't reach for an MCP; if the tool lacks a capability, extend it with a new verb rather than bypassing it.
- **Tickets are declarative outcome statements**, not task logs: an imperative title, a self-contained *Why*, one verifiable *Done-when*, and real links. Sequence lives in `blocks` relations, never restated in prose. Design depth belongs in the co-located agent doc the ticket links to, not inlined into the ticket body.

## Safety

- **Never bypass safety checks without asking.** When a tool, linter, or validation rejects an action, do not reach for `--force`, `--disable-*`, `--no-verify`, or any equivalent bypass flag. First: understand why the check exists. Second: look for an alternative that satisfies the check (e.g. use relative paths instead of disabling path validation). Third: if no clean alternative exists, explain the tradeoff and ask the user before applying the bypass.
- **Fix warnings; suppress only under a wrapped or tracked exception.** The default is to fix whatever a linter or type checker flags — a warning means the code is wrong. A suppression (`# noqa`, `# type: ignore`, `# pyright: ignore`, a per-rule config exclusion) is permitted in exactly two cases:
  1. **Fundamentally unavoidable** — the suppression covers something that genuinely cannot be written another way (a third-party library with no typed or public API, a type-checker-only construct). Isolate it behind a wrapper module (e.g. `torch_ops.py`, `tensor_types.py`), and declare that module with a lintable header comment as its first line — `# noqa-wrapper: <what it wraps and why>` — so the whole file is a recognized, auditable suppression boundary and the suppressions inside it don't each have to justify themselves. Even a single unavoidable suppression goes in such a module; there is no inline escape.
  2. **Deferred but tracked** — the warning exists because of work that isn't done yet, and that work is tracked by a ticket. The suppression must carry that ticket's id beside it, e.g. `# noqa: TID251 — tracked in PLE-233`. The ticket must be open; a suppression pointing at a closed or missing ticket is a regression or an unjustified suppression. When the ticket lands, the whole line goes.

  Case 2 is the one sanctioned exception to "comments are self-contained / no ticket pointers / no temporal language": a suppression is inherently temporary and coupled to the ticket that ends it, so naming that ticket is correct here where a normal comment would not. Every suppression is therefore mechanically classifiable — inside a `# noqa-wrapper:` module, or carrying an open ticket id — with no inline judgment-call escape; anything else fails the check, so fix the code or explain the blocker and let the user decide.
- **No ephemeral code artifacts.** Never generate files (scripts, plans, configs) that exist only to be executed once and deleted. If a workflow requires a throwaway artifact, redesign it so the tool does the work directly.

## Agent-facing documentation

Two audiences read a repo's docs: a human onboarding (`README.md`) and an agent working (`AGENTS.md`). This section governs the agent-facing tier.

- **One co-located doc per subsystem — always.** Each coherent subsystem has exactly one agent-facing doc at its directory root, named `AGENTS.md`, describing the subtree rooted there. There is no separate on-demand tier: a nested `AGENTS.md` auto-loads when a file in its directory is touched, so on-demand loading already happens automatically — a second file would be pure overhead. A subsystem is the smallest scope where the constraints stop being self-evident from the code; if a directory has no non-obvious constraints, it gets no doc.
- **Naming: `AGENTS.md` is canonical, with a one-line `CLAUDE.md` import beside it.** opencode reads `AGENTS.md`; Claude Code reads `CLAUDE.md` and does not natively read `AGENTS.md`, so each directory with an `AGENTS.md` also has a `CLAUDE.md` whose entire content is the import directive `@AGENTS.md`. Claude Code expands the import on load — verified for nested on-demand loads, not just the root — so the model gets the `AGENTS.md` content when it touches a file in that directory. It is a plain-text import rather than a filesystem symlink because a symlink does not survive checkout on native Windows without Developer Mode: Git silently writes it as a small text file containing the string `AGENTS.md` and the doc never loads, whereas the `@AGENTS.md` file checks out identically on every platform. When a directory needs Claude-specific additions, its `CLAUDE.md` keeps the `@AGENTS.md` line and appends below it.
- **The root doc is an index.** Root `AGENTS.md` (always loaded) carries terse cross-cutting rules, an index to the subsystem docs, and the `@AGENTS-SHARED.md` import. Depth lives in the subsystem docs, not the root.
- **What the doc holds: what a reader can't derive from the code.** The load-bearing content is constraints — authored choices ("we picked X because Y") and discovered invariants ("this non-obvious behavior exists because Y") that a reader would otherwise reverse-engineer from `git log` or rediscover the hard way. The code is the source of truth; the doc augments it. A doc that only restates what the code plainly says has no reason to exist — delete it.
- **Single-file-deep rationale goes in a block comment, not the doc.** When rationale is local to one file, a block comment at the relevant code is the right home — it sits with the thing it explains and can't drift away from it. The subsystem doc references such a comment rather than duplicating it.
- **Length discipline by pruning test, not line caps.** A nested doc injects in full on every touch of its directory, so keep it lean. The test is: "would removing this sentence cause an agent to make a mistake? If not, cut it." Architectural-overview narrative that doesn't help an agent locate code or make a decision is the first thing to cut. There is no line number that makes a doc good or bad.
- **Snapshot of present truth — no status markers, no history.** The whole doc describes the code as it is now. No "Future Work" / "Known issues" / "In flight" / "TODO" sections, no status frontmatter, no superseded-decision tombstones. If a constraint exists because an older approach failed, fold that into the new constraint's rationale; don't preserve the dead one. Git log is the audit trail.
- **No forward pointers into volatile artifacts.** A doc must not link to a specific ticket, memory, or bug id — those move and close; the doc outlives them. Cross-reference is one-way: tickets and memories link *to* the doc, never the reverse.
- **Diagrams are ASCII only.** No mermaid, no PNGs, no embedded images — ASCII renders identically in every viewer (web, editor, terminal, agent file-read). If a flow can't be sketched in 4–6 lines of ASCII, prose is the better tool.
- **No `docs/` directory for present-truth docs.** Documentation *of code that exists* co-locates as `AGENTS.md`; cross-cutting present truth lives in a parent-directory `AGENTS.md` or a top-level special file (`README.md`, etc.), never a separate docs tree. The one sanctioned separate tree is `design/` — the in-flux design/research tier below — which is deliberately *not* co-located because pre-implementation and cross-cutting design has no single subsystem to sit beside.
- **In-flux design and research lives in `design/`, a distinct tier from `AGENTS.md`.** Worked-out design for un-built or cross-cutting work — mechanism, math, alternatives, literature — goes in `design/` as plain, git-tracked Markdown, linked from Linear tickets by blob URL. It is explicitly pre-implementation, never auto-loaded, and *expected to go stale*: shipping code routinely outdates shelved design, and that is a property of the artifact, not a defect to enforce against. It is durable (survives a sandbox teardown, unlike a memory) but not authoritative about the current code (unlike an `AGENTS.md`); when a design is built, its hardened parts fold into the co-located `AGENTS.md` and the note stops being load-bearing. The tier is org-level and cross-repo, homed in the placeframe repo. See `design/AGENTS.md`.
- **Reference, don't recapitulate.** Point at code with `path:line`. No code blocks longer than ~8 lines unless the exact text is load-bearing.

## Code conventions

- **Python 3.13+**, line length 120, Ruff for linting/formatting, type checker in strict mode. Pydantic v2 for data validation everywhere; async/await throughout all services.
- All Python packages use `src/<package>/` layout with `py.typed` marker. Use relative imports for intra-package imports (`from .module import ...`, not `from package.module import ...`).
- **Imports must match declared dependencies.** Every imported package belongs in the relevant `pyproject.toml`. Don't import a transitive dependency without declaring it. Per-rule exceptions for platform-specific packages (CUDA/ROCm) are documented in each `pyproject.toml`.
- **Pin everything.** Never use `:latest` image tags, `stable` channels, `_latest` package URLs, or any mutable version reference. All images use content-addressed SHA tags; all base images use digest-pinned references. If a SHA tag doesn't exist in the registry yet, surface a clear error — don't fall back to a moving reference.
- **No shell scripts.** All scripting is Python. CI workflow steps should be one command (two at most). If there's a condition, a loop, or any real logic, it belongs in a Python script invoked via `uv run`, not inline shell in a workflow YAML, a `*.sh` file, or a heredoc embedded in another script.
- **Use the project's bash wrapper, not `subprocess`.** All shell-out from Python code goes through the project's `placeframe_bash` helpers (`bash()` / `bash_output()` / `bash_check()` / `bash_pipe()` / `bash_handoff()`). Don't reach for `subprocess.run` / `subprocess.check_output` / `subprocess.Popen` — those bypass the project's logging, error-handling, and shell-operator guards. For idempotent operations where failure is expected (zone already exists, interface already bound), use `bash_check()` — never `try: bash(...); except CalledProcessError: pass`, which prints spurious errors and swallows Ctrl+C.
- **`bash()` / `bash_output()` reject shell operators.** The `_check_no_pipe` guard strips quoted strings and rejects any `|` — this catches both pipes (`|`) and logical OR (`||`). Don't use shell fallback patterns like `cmd || echo default`. Instead, use `bash_check()` to test success, then `bash_output()` for the value. `bash_pipe()` is only for actual pipelines (`cmd1 | cmd2`).
- **No inline imports.** All imports at module level. No `from x import y` inside functions or methods.
- **Comments**: Plain `#` only. No section dividers (`# ---`), no decorative formatting. Comments should be rare — prefer self-explanatory code. When a comment is needed, keep it short and factual.
- **No docstrings.** Do not add docstrings to functions, classes, or modules — no exceptions.
- **No temporal language in comments.** Don't write "Phase N", "currently", "for now", "until X lands", or other tense markers anchored to a moment. A comment should describe what the code does now; temporary scaffolding gets tracked in a per-initiative plan file, not inline. Comments that survive into a different temporal context become misleading.
- **Comments must be self-contained.** A comment shouldn't require chasing a design doc, ticket, or chat history to make sense. "See TDD" / "as discussed in spec" pointers imply context without delivering it. Inline the full rationale or omit the comment. Cold-reader test: if every external doc were deleted, would this comment still make complete sense?
- **Variable names**: Always use full words, never abbreviations. `result` not `res`, `command` not `cmd`, `environment` not `env` (as a variable name — `env` as a keyword argument is fine). Exception: universally understood short names like `i`, `k`, `v`, `e` in tight scopes.
- **Typer entry points**: Scripts using `typer.Typer()` with `@app.command()` must use `:app` as the entry point in `pyproject.toml`, not `:main`. Calling `:main` bypasses typer's CLI argument parsing. Scripts that don't use typer (plain functions) use `:main` as normal.
- **Typer parameters**: Use `Annotated` types, not default values, for `typer.Argument` and `typer.Option`. This avoids B008 (function call in default argument). Example: `spec_file: Annotated[Path, typer.Argument(help="...")]` not `spec_file: Path = typer.Argument(..., help="...")`.
- **Callers before callees.** When one function in a file calls another defined in the same file, the caller's definition appears earlier (closer to the top). Module entry points / public API live near the top; leaf helpers live at the bottom. Among sibling callees called by the same parent, order them by their first call site within that parent's body.
- **Classes at the top.** All class definitions live at the top of the file, immediately below imports and module-level constants and above the first `def`. This applies even when a class is used by only one function — data shapes belong with the file's structural declarations, not interleaved with behavior. The "callers before callees" rule orders functions; it does not push classes down to where they are first referenced.
- **Prefer declarative over imperative.** R3/LINQ operator chains over while loops with multi-predicate exit conditions; joins over dict-mutate-in-foreach; pre-computed view records over inline ternaries in copy lambdas. Reach for imperative only when the declarative version genuinely loses a behavioral guarantee — verify by auditing the code, not by assuming. The default answer to "is the declarative rewrite worth it?" is yes.
- **Inline single-call helpers, except when they own a `try` block or are an idempotency-guard predicate.** If a function is called from exactly one place, prefer inlining at the call site. Two exceptions: (1) a helper that contains its own `try` block (`try/except`, `try/finally`, or `try/except/finally` — and the same shape in C#/Java's `try/catch`/`try/finally`) stays a function — inlining puts a nested `try` inside the caller's `try`, which is harder to read and harder to extend. (2) Small named-guard helpers (`need_X_action() -> bool` shape) that bundle a presence check with skip/doing logs stay as helpers — the function name documents what's being guarded, and inlining strips that signal back into a generic `if/else` pair.
- **Don't catch what you can't handle.** A `try` block must be one of exactly two shapes. **(a)** Catching a *specific*, anticipated, *exogenous* failure (network timeout, file-not-found, malformed external input, expected cancellation, a library that raises instead of returning a sentinel) with a *specific* recovery — always the narrowest exception type that matches, never base `Exception`/`Throwable`. **(b)** A top-level boundary of a long-lived loop (worker poll loop, HTTP request handler, supervisor, top of `main`) catching base `Exception` solely to log it as **Error** and then continue or terminate cleanly. Anything else is *Pokémon exception handling* — "gotta catch 'em all" — defensive over-catching: swallowing bugs under `try/except: pass`, a bare `try/finally`, or a `try/catch (Exception)` that just carries on. Uncaught exceptions in business logic are by definition code bugs — surface them loudly at the top-level Error log; don't wrap a block "in case something goes wrong." If you can't name what the `try` is catching and why, delete it.
- **No nested `try` blocks.** A `try` (with any combination of `except`/`finally`, or C#/Java's `catch`/`finally`) inside another `try`'s body should be extracted to a helper. The helper's own scope absorbs the inner handler and the outer `try` reads as a single step.
- **Guard clauses; invert if-blocks for early return.** When a long body sits inside `if X:`, invert to `if not X: continue` (or `return`) and let the long path live at the function's natural indentation. Saves indent levels and keeps the happy path linear.
- **Matched brace style across adjacent control flow.** In C# and Java, two adjacent `foreach`/`if`/`for` statements should both use braces or both not. Never have a brace-less control statement whose body is itself another control statement — that's the [Apple `goto fail`](https://www.imperialviolet.org/2014/02/22/applebug.html) shape, where a future line addition silently lands outside the intended loop.
- **Blank lines.** Add a blank line after every `try` block, and between larger `if` blocks within the same function.
- **Extract threadpool / async lambdas to named methods.** A multi-line lambda passed to `Task.Run`, `UniTask.RunOnThreadPool`, etc. should be a named instance or static method. Lambda boundaries obscure intent in stack traces and bloat the call site.
- **Unity: UniTask, not `Task.Run`.** Unity code uses `Cysharp.Threading.Tasks` everywhere. New offloads use `UniTask.RunOnThreadPool(...)`. `Task.Run` is only acceptable when an override signature requires returning `Task<T>` — and even then, the inner offload should use UniTask (await unwraps fine inside an `async Task<T>`).
- **Unity: avoid Java for non-trivial logic.** Bespoke Java is hard to audit from a C#-focused review. Use Java only for mechanical SDK glue (10–30 lines wrapping an Android API or handing bytes to a library), and keep all real logic in C#. If a task seems to need substantial Java, look for an `AndroidJavaObject` / `AndroidJNI` expression in C# first.
- **Serilog message templates, never interpolated strings.** Every `Log.X(...)` call must pass a constant message template with `{PascalCaseNamed}` placeholders and the values as separate `params object[]` arguments — never `$"..."` interpolation, `string.Format`, or pre-rendered strings. Example: `Log.Info(LogGroup.Zed, "AOA req id={RequestId} {Method} {Path} body={BodyLength}B", requestId, method, path, bodyLength);` — not `$"AOA req id={requestId} ..."`. The enricher captures each named placeholder as its own queryable field in Loki; interpolation bakes the values into the string and destroys that structure. Pass exceptions as a typed argument (`Log.X(group, exception, "template", ...)`), not interpolated — the structured exception block only attaches when `LogEvent.Exception` is set. Applies to Python logging too: `logger.info("req id=%s %s %s", id, method, path)`, not an f-string.
- **Log levels: only Info and Error are meaningful in practice.** Two effective levels. **Info**: lifecycle events, transient failures (network blips, expected disconnects), non-success HTTP responses with status `< 500`, caught exceptions that don't represent a code bug (`IOException`, `OperationCanceledException`, `AndroidJavaException` wrapping an AOA pipe failure). **Error**: a code-side bug. `NullReferenceException`, `ArgumentException`, invariant violations, `5xx` responses from our own services. **Warn**: rare; reserved for degraded-but-still-functioning states (partial success, fallback taken, unhandled developer-facing case). Do not use Warn for transient connectivity failures. **Trace/Debug**: rare; reserved for subsystem-specific debugging.
- **`typing.cast` is forbidden unless there is literally no other way.** A `cast` asserts a fact to the type checker that the type checker cannot verify — it's a programmer promise, not a proof, and it rots silently when the underlying types drift. Before reaching for `cast`: (1) make the upstream type more precise (annotate the producing function, narrow the source); (2) reconstruct the value in a typed way (explicit dict-comprehension over `.items()`, field-by-field copy into a typed container); (3) validate with a typed schema library (pydantic, msgspec) that returns a typed object. Only when all three are infeasible does `cast` become acceptable, and the call site needs an inline comment naming the specific constraint that ruled out (1), (2), and (3). The same prohibition applies to `# pyright: ignore` and assigning a typed value to a deliberately broader-typed variable to escape narrowing.

## Unity NuGet packages

Unity projects use [NuGetForUnity](https://github.com/GlitchEnzo/NuGetForUnity) with `packages.config` files. The NuGetForUnity CLI (`dotnet nugetforunity restore`) only downloads packages already listed — it does **not** resolve transitive dependencies. Dependency resolution only happens through the NuGetForUnity editor UI inside Unity.

**When adding a NuGet package to `packages.config`**, you must also add its transitive dependencies manually. Check the package's **.NET Standard 2.0** dependency list on nuget.org (e.g. `https://www.nuget.org/packages/Serilog/4.0.1`). Skip low-level BCL packages that Unity's runtime already provides (e.g. `System.Buffers`, `System.Memory`, `System.Numerics.Vectors`, `System.Threading.Tasks.Extensions`). Add higher-level transitive deps like `System.Text.Json`, `System.Diagnostics.DiagnosticSource`, etc. Missing transitive deps won't cause compile errors locally in the editor (NuGetForUnity resolves them there), but they **will** fail in CI where only `restore` runs.

## Docker build context

- **`.dockerignore` is an allowlist.** It uses `*` (ignore everything) then `!` entries to whitelist paths Docker can see. This file is the single source of truth for which files affect Docker image builds and for the `CONTEXT_SHA` image tag. Adding a COPY for a path not in the allowlist fails the build loudly (self-correcting). Extra entries cause unnecessary rebuilds (safe failure mode). When adding a new directory that a Dockerfile COPYs, add a `!` entry to `.dockerignore`.
- **BuildKit does not expose which context files a build uses.** Despite computing this internally (`FollowPaths` in the LLB solver), there is no API or CLI to query it ([moby/buildkit#1181](https://github.com/moby/buildkit/issues/1181), open since 2019). This is why we use the `.dockerignore` allowlist approach rather than inferring build inputs from Docker.

## Open audit

Several rules above are convention-only when they could be mechanically enforced (e.g. no-docstrings → Ruff `D100`–`D107`; no-inline-imports → Ruff `PLC0415`; subprocess ban → import-linter or a custom AST check; `:latest` ban → a grep step in preflight). Others aren't trivially lintable (callers-before-callees needs call-graph analysis). The split between "convention" and "lint" is unaudited; this is a placeholder so the question gets revisited intentionally, not a scheduled task.
