# zed-capture SPEC

## What this is

The zed-capture service runs on the ZED Box (a Jetson appliance with a stereo ZED X camera attached over GMSL2) and turns physical-world stereo captures into a serializable tar package that the rest of Placeframe consumes. It exposes a REST API to the phone-side CaptureTool over USB-OTG via the AOA bridge, and emits per-frame stereo JPGs plus a gravity-stamped manifest into a session directory that is later streamed back to the API as a tar.

## Shape

The runtime is a `threading.Thread`-based actor.

- `src/zed/zed.py` — `Zed` is the camera actor. `start_capture` / `stop_capture` enqueue command messages; the actor thread owns the SDK handle and serializes all SDK calls onto its own thread. `Zed.run()` polls the command queue and ticks the camera between commands. `Zed._tick()` is the per-tick body. `Zed._advance_tracker()` calls `grab()` + `update_pose()`; `Zed._persist_current_frame()` writes a stereo JPEG pair and a `frames.csv` row.
- `src/zed/zed_wrapper.py` — thin pyzed `sl.Camera` wrapper that converts SDK error codes to Python exceptions and pose getters to numpy arrays. The single boundary between Python and the C-bound SDK.
- `src/zed/zed_stub.py` — non-rig stub for running without a camera attached. Used for shape-only tests.
- `src/routers/captures.py` — REST surface (`/start`, `/stop`, `/captures`, `/captures/{id}` tar download). Endpoints dispatch to the actor via the worker-thread pool.
- `wait_for_zed_camera.py` — boot guard that blocks until both nvargus's socket is connectable *and* `/dev/video0` + `/dev/video1` exist before the stack starts. See "Start the stack from the systemd unit, not the docker restart policy" below.
- `compose.rig.yml` + `placeframe-zed.service` — box-side compose overlay and systemd unit installed by `install-zed`.

## Constraints

### Drive `grab()` on every loop iteration

**Context:** The ZED SDK's positional tracker integrates IMU and visual frames inside `grab()`. A naive design that calls `grab()` only on capture-interval boundaries (e.g. once every 500 ms for a 2 Hz persistence cadence) starves VIO — the tracker needs samples at the camera's native ~30 Hz to maintain a stable pose estimate. Gating `grab()` on the capture interval produces meter-scale drift across multi-meter scans.

**Constraint:** `Zed.run()` calls `grab()` every loop iteration. The actor's queue timeout is `0.0` while a capture is active so the loop spins at the SDK's native cadence — `grab()` itself blocks until the next frame is available, providing natural backpressure. `_persist_current_frame()` is gated on the capture interval; `_advance_tracker()` is not. The two cadences are independent.

**Consequences:** Adding a code path that gates `grab()` on the capture interval is forbidden — it has been tried and produces unusable drift. Any future "save power" or "drop camera FPS to 10 Hz" change must preserve the invariant: tracker updates happen at whatever rate `grab()` returns, never less frequently than the persistence cadence.

### Warm up the tracker before persisting the first frame

**Context:** `enable_positional_tracking` starts the tracker in `SEARCHING`; it needs a beat of motion plus IMU settle before its scale and gravity-aligned world frame converge. A capture that persists from the moment Record is pressed writes those cold-start poses into the head of the trajectory — the worst-residual frames in every audited session — and they seed the first sequential pairs the reconstructor builds.

**Constraint:** On `/start`, `_start()` opens the camera and enables tracking, but `_next_capture_time` stays `None` (no persistence). The actor advances the tracker every loop and begins persisting only once `get_position()` returns `POSITIONAL_TRACKING_STATE.OK` for `STABILIZE_REQUIRED_OK_FRAMES` consecutive grabs, or `STABILIZE_BACKSTOP_SECONDS` elapses. `state()` exposes `tracking_state` and a `stabilizing` flag (capture active, not yet persisting) through `/status`; the phone shows a "hold still and level" banner while `stabilizing` is true and disables Stop until it clears.

**Consequences:** The first persisted `frames.csv` row comes from an `OK` tracker, not `SEARCHING`. The SVO recording still spans the warm-up window — it is enabled in `_start` and not gated — but nothing downstream consumes it. A capture cancelled during warm-up persists zero frames and never reaches `/stop`, so no tar is built and `get_capture_sessions` does not enumerate the orphan; the placeholder meta lingers on disk until the operator deletes it.

### Run with `DEPTH_MODE.NONE`, `depth_stabilization = 0`, and `POSITIONAL_TRACKING_MODE.GEN_3`

**Context:** The SDK 5.2 default depth mode is `NEURAL`, which dominates per-grab cost on the Jetson and was capping `grab()` cadence at ~10 Hz with depth on, vs the camera's native 30 Hz. Nothing downstream of the box consumes depth: the reconstructor runs its own COLMAP SfM from the persisted JPGs + `frames.csv`, and the localizer matches features against the SfM map. Stereo disparity computed by the SDK is thrown away every grab.

**Constraint:** `Zed._start()` sets `init.depth_mode = DEPTH_MODE.NONE`, `init.depth_stabilization = 0`, and `PositionalTrackingParameters.mode = POSITIONAL_TRACKING_MODE.GEN_3` explicitly. GEN_3 (introduced SDK 5.2, default since 5.2.0) is a feature-based VSLAM tracker that operates without depth. `depth_stabilization = 0` is not an optimization: with the default value the SDK runs depth in the background to "stabilize" tracking even when `depth_mode` is `NONE`, defeating the disable. GEN_3 is pinned explicitly rather than relying on the SDK 5.2 default so a future SDK bump can't silently flip the tracker back to a depth-dependent mode.

**Consequences:** The "Enabling positional tracking" log line emits `mode=GEN_3 depth_mode=NONE depth_stabilization=0` and is the verification signal in Loki. Area memory (loop closure / relocalization) still works under GEN_3 + NONE per Stereolabs docs. Any future feature that would re-enable depth (e.g. on-device occlusion-aware AR overlay on the box itself) re-introduces the cadence regression and must explicitly justify paying that cost.

### Start the stack from the systemd unit, not the docker restart policy

**Context:** The compose stack has one boot-time race that the unit must arbitrate. `/dev/video0` and `/dev/video1` must exist on the host before zed-capture's container is created: the Stereolabs SDK opens them directly, and the nvidia container runtime (in CSV mode) injects Tegra device nodes into the container's tmpfs `/dev` at container-creation time by scanning the host for matching paths — nodes that do not yet exist on the host are silently skipped, and the SDK's later `open("/dev/video0")` returns `ENOENT`, surfacing as `ERROR_CODE::CAMERA_STREAM_FAILED_TO_START`. The V4L2 nodes are created by udev only after the GMSL pipeline brings the sensors up (`nvargus-daemon` socket vs `sl_zedx` kernel module + udev are independent paths on independent timers), routinely lagging the docker daemon by tens of seconds to minutes. If any compose service is set to `restart: unless-stopped` or `restart: always`, dockerd auto-starts that container the moment it itself starts — losing the race against udev.

**Constraint:** Compose-service restart policy is `restart: on-failure`. `on-failure` retains in-operation crash recovery without triggering boot-time auto-start (`unless-stopped` and `always` both auto-start; `on-failure` and `no` do not). At boot, `placeframe-zed.service` is the sole starter: `ExecStartPre=wait_for_zed_camera.py` blocks until `/dev/video0` + `/dev/video1` exist and the argus socket is connectable; `ExecStart=docker compose up -d` then creates containers under known-good preconditions. No `--force-recreate` is necessary — without `unless-stopped`, there's no zombie container to defeat.

**Consequences:** Switching any service back to `restart: unless-stopped` (or `always`) reintroduces the V4L2 race; dropping `wait_for_zed_camera.py` reintroduces the V4L2-zombie. The unit being the sole starter at boot also means a whole-stack outage after first activation doesn't self-heal — individual container crashes are covered by `on-failure`, but if every container exits cleanly the unit stays `active (exited)` and won't re-run without `systemctl restart placeframe-zed.service`. This is intentional: a coordinated stack exit indicates a deeper problem that should surface as an outage rather than silently self-repair. `install-zed` deliberately bypasses the unit and runs `docker compose down + up -d` directly, so a fresh-box install can complete before the camera is attached — routing through the unit would block on `wait_for_zed_camera` and fail the install.

### Treat the box's wall clock as untrusted end-to-end

**Context:** The Jetson has no battery-backed RTC and runs offline during field operation, so the box's wall clock is never authoritative: a cold boot lands at the 1970 epoch and there is no NTP source to refine it. A `datetime.now(tz=UTC)` call inside zed-capture is as likely to return 1970-01-01 as a date near the present. Two consumers used to depend on an accurate box clock and both now read the phone's instead. Capture metadata: a 1970-stamped `recorded_at` propagates through the placeframe API, MinIO bucket prefixes, and reconstructor lease objects until an operator notices. Box-side logs: `docker/loki/box.yaml` had a 2024 `schema_config` floor (Loki crash-loops at boot when the clock predates it) plus `reject_old_samples` (drops stale-looking ingest), and the system leaned on `fake-hwclock` restoring a past-2024 snapshot to keep that floor satisfied — a clock the box had no other reason to keep accurate.

**Constraint:** zed-capture never samples wall-clock time for anything that escapes the box. Capture metadata: `POST /capture_sessions/start` requires a `started_at` `AwareDatetime` in the request body; that value is written into `CaptureMeta.recorded_at`, survives unchanged through `/stop` and `get_capture_sessions`, and supplies the placeholder name. Logs: box-side Loki is configured clock-insensitive — the `schema_config` floor is the unix epoch and `reject_old_samples` is off — so a 1970 boot neither crashes it nor drops ingest. The phone's `LogDrainController` operates entirely in box time and converts to phone time only at the push boundary. box-Loki is paged by time range and its entries carry box time, so the drain probes the box clock from a Loki response `Date` header and builds both its query window and its forward cursor in box time — paging in phone time would never overlap the box's entries and silently drains nothing the moment the clocks diverge (the exact failure the box-time treatment exists to prevent). It then restamps each retrieved entry by `phone_now − box_now` before pushing to the backend (which still enforces its own schema floor and would reject 1970-stamped entries). Per-frame `timestamp_ms` in `rig0/frames.csv` still comes from the ZED SDK's clock and is absolute-unreliable, but downstream consumers read it only for relative ordering and pair generation.

**Consequences:** Nothing on the box requires an accurate wall clock, so there is no `fake-hwclock`, no clock-restore boot-ordering, and no NTP dependency — `install-zed` provisions none of them. Re-introducing any `datetime.now()` in the capture-metadata path reintroduces the 1970-capture symptom. Re-adding a recent `schema_config` floor or `reject_old_samples` to `box.yaml` reintroduces the box-Loki-crashes-at-1970 symptom: box ingest goes silent and the phone-side drain returns 502 / empty. The drain restamp depends on the box emitting a `Date` header on the Loki query response; absent it, the drain tick fails rather than pushing backend-rejected timestamps. Within a single boot the restamp is exact; logs left undrained across a box reboot — which restarts the box clock at 1970 in the persistent `aoa-loki` volume — share a timestamp range with the next boot's and anchor to the wrong offset, an accepted edge case since the drain runs continuously while the phone is connected.
